## 结论

连续性断言**结构上不可满足**，建议换成一条可满足且能抓真实错漏的不变量。
唯一性断言应保留。

## 论据一：并发分支下无解

各 agent 在各自分支上从 main 的最大序号往后取号。设 main 当前最大为 30：

- A 取 31，B 取 32
- **若 B 先合并**：main 变成 `1..30 + 32`，缺 31 → 断言变红
- 若 A 先合并：main `1..31`，B 合并后 `1..32` ✓

也就是说，**两条分支各自都合规，合并结果却可能不合规**，取决于合并顺序 ——
而合并顺序不由取号者决定。

**加锁解决不了。** 仓库里已有 `tools/mergeguard` 的锁（`git_common_dir/merge-lock/`，
带 PID 存活检测与 TTL，跨 worktree 共享）。锁能让取号**串行**，但改变不了合并顺序：
先取到 32 的人仍可能先合并。

唯一能保住连续性的做法是**在合并时重新编号**。那正是此前反复出现的 churn：
`claim-nullable` 违规记录要求「序号按认领时间重排」、Qoder 复核发现 ② 也是重排，
本次提出者为让文件序号合规改了三次（31→33→34，每次都因为别人先占了号）。

## 论据二：连续性没有防住唯一性没防住的东西

原注释（`discipline.py` L241-242）给出的理由是：

> 序号即身份：除唯一外还必须连续为 1..N，否则撞号可以靠「跳号」规避

这个推理把两件事混为一谈：

- **留空隙**（1,2,4,5）：本身无害。文件不会因为缺 3 而失去身份 ——
  身份由`task_id` 承担，且唯一性断言已经在查它。
- **逃避检测**：无论是否跳号，重复号都会撞上唯一性断言。跳号不提供任何掩护。

能构造出的最坏情形是「有人删了一个认领文件」—— 那会留下空隙。但连续性只**显示**
空隙存在，不告诉你删了哪个、也不阻止删除；而 `merge` 组已经从 git 历史反向核对
「已合入 main 的分支都在认领表登记」，那才是直接管删除/遗漏的断言。

## 建议的替换

保留：`认领文件序号唯一`、`一个 task_id 只对应一个认领文件`（两条都保留）。
替换：`序号连续为 1..N` → **`文件名里的 task_id 与文件内容的 task_id 一致`**。

后者同样能抓真实错漏（文件被改名、放错任务、复制后忘改内容），而且两个 agent
独立操作也能同时满足 —— 它不依赖任何跨分支的共享计数器。

序号前缀**建议保留**（人读时便于排序），只是不再断言连续。认领顺序本来就在每个
文件内部有 `认领时间` 字段，不依赖文件名。

## 若决定保留连续性

那需要接受以下之一，请拆分者与 `mergeguard` 归属方权衡：

1. **合并时统一重编号**：由 `mergeguard` 在合入时重排 `docs/claims/` 的文件名。
   代价：每次合并多一步写操作，且会改动他人分支上已登记的文件名。
2. **取消跨分支并发取号**：要求所有认领先在 main 上串行完成（用 `mergeguard`
   的锁），再开工。代价：与「登记在自己分支上做，避免冲突」的拆分初衷相反。
3. **接受偶发不合规**：保留断言，靠合并顺序碰运气，不合规时人工重编号。
   —— 这是当前的事实状态，也是 churn 的来源。
