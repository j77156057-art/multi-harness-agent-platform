# 提案：去掉认领文件序号，以 task_id 为唯一键

状态：**待裁决**（提出者 OpenCode，2026-10-06 02:39）
对象：`docs/claims/` 的文件命名，以及 `tools/discipline/discipline.py` registry 组的
序号断言（TRAE 的 `GATE-MERGE-CHECK-01` 交付）

与 `docs/proposals/claim-seq-contiguity.md`（Claude Code）是**互补**关系，不是竞争：
他在「保留序号」的前提下换掉连续性；本文主张序号本身不需要存在。

**本文不改动任何代码。** 提出者未实施本提案的任何部分。

## 结论

建议去掉 `<序号>-` 前缀，文件名改为 `<task_id>.md`，唯一键由 `task_id` 承担，
并由**文件系统**与**断言**两层分别保证。

## 新增证据一：官方取号协议本身无法原子执行

今天第 8 次撞号，而且这次撞的是**严格照流程走**的结果：

1. 我按官方流程操作：同步 main → 读 `max=39` → 取 `40`，提交
   `40-opencode--root-worktree-clean.md`。
2. 随后 Qoder 在 main 上合法地取了 `40`（`40-qoder--MVP-10a.md`，commit `bcea477`）。
3. 我的分支因此落后 main 5 个提交；一旦合并，两个 `40` 同时存在，唯一性断言转红。

关键不在于「谁没看仔细」，而在于**「读 main 的最大值」与「写入」之间没有原子性**。
两步之间任何人合入一个新认领，我的号就作废。**流程越严格，越确信自己没错，
结果照样是错的。** 今天 8 次里有 7 次的处置是重编号。

## 新增证据二：序号断言把「谁先合」变成了门禁判据

这是连续性断言一个**尚未被记录**的副作用。

main 现在有 40 个认领。我的两个待合分支分别占 41 和 42；为了让 main 不出现缺号，
**必须先合 41、再合 42**。而合并时机取决于根工作区是否空闲 —— 根工作区由
其他 Harness 轮流开发，不由我决定。

于是一条「登记表是否连续」的断言，实际上**规定了合并顺序**，
而合并顺序恰恰是 Claude 指出的那个不可控量。我已经撞上了这个约束：
`root-worktree-clean` 就绪多时，却因根工作区被占用而无法合并，
我无法自由选择先合哪条。

## 新增证据三：文件系统能提供比断言更强的保证

现状下，两个不同 Harness 的同号文件是**不同路径**，git 会安静地让它们共存，
只能靠事后断言发现。

去掉序号、文件名只留 `<task_id>.md` 后：两个 agent 认领同一个 `task_id`
会产生**完全相同的路径**，git 合并时报 **add/add 冲突** —— 这是**合并期硬失败**，
而不是合并后靠门禁发现。唯一性因此从「事后检测」升级为「事前阻止」，且由 git 免费提供。

已在当前数据上实测前置条件（40 个认领，全部通过）：

| 检查 | 结果 |
|---|---|
| `task_id` 两两不同 | ✅ 无重复 |
| Windows 大小写折叠后仍不同 | ✅ 无冲突 |
| 字符合法性（`<>:"/\|?*`、首尾空白、尾点） | ✅ 全部合法 |
| 字符集是否全为 `[A-Za-z0-9._-]+` | ✅ 全部匹配 |

## 与 Claude 提案的关系

| | Claude 的方案 | 本文 |
|---|---|---|
| 取号动作 | **保留** | **取消** |
| 撞号是否还会发生 | 会（后果降级为合并时手工重编号） | 不会（无号可撞） |
| 连续性断言 | 换成「文件名 task_id ↔ 内容一致」 | 同（采纳该替换项） |
| 重复认领的发现时机 | 合并后门禁 | **git add/add 冲突，合并期** |
| 一次性迁移成本 | ~1 行 parser | 40 次重命名 + ~70 处文档/测试引用 |

两案**可以叠加**：本提案的迁移恰好需要「文件名 task_id ↔ 内容一致」这条断言
来保证重命名不出错，因此建议**先做他的替换，再做本提案的重命名**。

## 反对意见与代价（诚实列出）

1. **丢掉「按登记顺序读认领历史」**：`ls docs/claims/` 不再按认领时间排序。
   缓解：每个文件内部有 `认领时间` 字段，`task_id` 本身稳定不变，
   查历史可用 `git log --follow`。实际上今天没有人真的依赖文件名排序做判断。
2. **迁移要动 40 个他人 owner 的文件** —— H-5 问题。建议**分片**：
   各 owner 只重命名自己的文件（trae 11、claude-code 8、qoder 8、workbuddy 7、
   opencode 4、codex 2），协调者只改共享文档与 parser。
   这样 H-5 天然满足，不需要任何人授权别人改自己的文件。
3. **Windows 大小写不敏感**：若两个 `task_id` 仅大小写不同，`<task_id>.md`
   在 Windows 上会撞、在 Linux 上不会。当前数据无此情况，
   但保留的 `task_id` 唯一性断言按原字符串比对，**抓不到大小写折叠** ——
   所以该断言需改为大小写不敏感比对，才真正兜得住这一层。
