目标：**把「在一台新电脑上接一个新 harness」的流程写成一份能照着做的手册**，放进仓里。

为什么：仓库主人问「那如果放到一台新电脑上，怎么添加新的 harness」，随后把
「把这份流程写进仓」圈了出来 —— 这套流程现在散在代码、卡片与我的回答里，
换台机器的人得自己拼。

范围：新增 `docs/harness-onboarding.md`（一份手册，**不碰代码**）。

手册要写清（全部对着代码核过）：

1. **两种「加入」不是一回事**：当**成员窗口**（CLI 装在成员机器，worker 去调它）
   与当**额度来源**（CLI 装在平台机器，池子自己去调它）—— 文件、机器、记账方式
   全不一样。
2. 五个步骤：装 CLI 并登录 → 写声明（新 CLI 才需要）→ 办公室登记基座与注册窗口 →
   发平台令牌并起 worker → （可选）加池子槽位。
3. 哪些文件在哪台机器上（声明在平台侧、二进制在成员侧；池槽位的 CLI 装在平台侧）。
4. 两个容易踩的坑：**仓库要共享**（平台合并时 fetch 的是它自己那份
   `canonical_repo`）、**声明里的 `tier` 必须人声明**（平台不猜）。
5. 什么时候才需要写代码（声明说不清 CLI 的行为时）。
6. 出问题先看哪里（界面上的四个原因码 → 含义）。
7. 真相源索引（每一步指向实现它的代码位置，避免手册烂掉）。

**不碰** `docs/spec/**`、不碰代码、不动其他 Harness 的工作区与分支。

## 怎么做到不出错

1. **手册里的每个事实都要对着代码核过**（声明字段与拒绝规则、实例 id 规则、
   令牌签发与计数、worker 参数与 enforce 前置、池槽位合并与档位、原因码）。
2. **只写流程，不发明规矩**：该由人声明的（tier、声明文件本身）写清是人的动作。
3. 手册里的路径与命令**能被人照着跑**：命令用仓库里真实的入口。
