## 2. 目标

构建一个项目级 Agent 协作平台，统一协调：

- TRAE；
- WorkBuddy；
- Qoder；
- Claude Code；
- Codex；
- OpenCode。

平台需要保证：

- 任务不会重复领取；
- 一个 Harness 领取多个任务时每个任务都有独立负责人和时间；
- 任务有依赖、产出和资源关系；
- 每个任务有独立 Git worktree 和分支；
- Harness 失联后可以恢复或接手；
- 完成结果有可验证证据；
- 旧 Harness 的过期写入不能进入集成分支；
- 未经审查和门禁验证的代码不能合并；
- 所有关键操作可排序、可重放和可审计。

## 3. v1 架构决策

v1 采用 Harness 主动拉取模型：

- Harness 自己运行 CLI 或执行环境；
- Harness 通过 API 查询任务、领取任务、发送心跳和提交结果；
- 调度中心负责任务状态、租约、权限、证据、审查和合并；
- v1 调度中心不统一启动和控制所有 Harness 进程；
- 统一 spawn、PTY 和推送模型留到后续版本。

因此：

- CLI、无头模式、API、MCP、ACP 或 A2A 是 v1 的可靠接入条件；
- 只有 GUI 的 Harness 不进入 v1 可靠执行路径；
- TRAE、WorkBuddy、Qoder 必须先通过能力探测；
- v1 先在一台 Windows 机器上运行；
- 多机器、远程 Worker、PostgreSQL、Redis 和 Docker 作为后续阶段。



### R8 宿主与发布模式（ADR-058）

v1 的 Harness 宿主模式必须在注册时固定为 `native_cli`、`ao_managed_git` 或
`patch_apply`，不得在一次 attempt 中途切换。阶段 0 的默认决策是：

- Codex、Claude Code、OpenCode 等可执行自身 Git 的 Harness 使用 `native_cli`，
  调度中心只提供协议、能力、费用和审计旁路；
- Agent Orchestrator（AO）托管的 Harness 使用 `ao_managed_git` 时，AO 仅对
  任务 worktree 路径放开 `add/commit/checkout/switch` 等写操作，禁止 push、force、
  rebase 到非任务分支，并同步更新 AO 的命令 deny-list 与源码级只读测试；
- AO 无法安全放开 Git 写操作时使用 `patch_apply`。Harness 上传 patch，调度中心在
  任务 attempt 的临时对象库中 apply，生成归属于该 attempt 的新 commit，再执行同一
  Verify、receipt、fencing 和 Merge Gate。patch 的 hash、应用者、生成 commit 和
  fencing epoch 必须进入 `artifacts`、`task_events` 和 `side_effect_intents`。

阶段 0 必须给每个 Adapter 写明宿主模式、Git 写能力、head_commit 来源和失败时的
`submit_result` 行为。没有可靠 commit 或 patch 证据的 Adapter 不得进入 v1 可靠执行路径。

## 5. 系统结构

~~~text
React 前端
  │ REST / WebSocket 事件订阅
  ▼
调度中心
  ├── 项目、群组和消息
  ├── 方案、任务 DAG 和产出契约
  ├── 原子 Claim、Lease、Heartbeat、Retry
  ├── Harness 注册和能力门控
  ├── Worktree、资源 Lease 和 fencing
  ├── Verify、Review Gate、Merge Queue
  ├── 事件日志、Outbox 和恢复
  └── 审计、指标和告警
        │
        ├── SQLite + WAL
        ├── Git 仓库
        └── 各 Harness 自己运行的执行环境
~~~

推荐：

- 后端：Go；
- 前端：React、TypeScript、Vite；
- 数据库：SQLite、WAL、busy_timeout；
- Git：Git CLI 和 Git worktree；
- 实时事件：WebSocket 只读订阅；
- 外部协议：v1 以 HTTP/JSON 为主，MCP、ACP、A2A 作为 Adapter profile；
- Windows 终端调试：作为后续可选能力，v1 不依赖统一 PTY；
- 代码和 Diff：Monaco 或 Diff Viewer；
- 任务图：React Flow。
- v1 REST 和 WebSocket 默认只绑定 localhost；远程访问、反向代理和 PostgreSQL 迁移属于后续安全边界变更，必须重新评审。

## 6. 项目、群组和 Harness

一个项目可以拥有多个群组：

~~~text
商城项目
├── 登录模块群
├── 支付模块群
└── 后台管理群
~~~

每个群组拥有独立的：

- 方案和方案版本；
- 任务和依赖；
- Harness 成员；
- 消息和未读状态；
- worktree 和资源；
- 审查、合并和审计记录。

Harness 注册至少包括：

~~~yaml
harness_id: harness-1
name: Claude Code
provider: anthropic
adapter: claude-cli
adapter_version: 1.0.0
capabilities: [backend, testing, review]
max_parallel_tasks: 2
status: online | degraded | offline
running_tasks: 0
registration_version: reg-003
~~~

能力来自 probe 结果和人类维护的注册表。运行时自报只用于告警或降级，不能单独用于高风险任务 Claim。

注册信息变更必须保留历史。任务 Claim 时固定注册版本。

harness_sessions 只记录 Harness 自报的会话元数据、注册版本和最后心跳，不代表调度器拥有或控制 Harness 进程；v1 拉取模型下不得把它当作 spawn/session 控制表。

R10 字段口径（消除 R9 的三处命名与落点缺口）：

- `tasks.attempt_no` 是当前已创建的最大 attempt 序号，Claim 事务内在创建 attempt 的同一步
  写入；它是 §11 Claim SQL 的 `attempt_no < max_attempts`、§10 五条 attempt 预算 guard 和
  §28 attempt 预算不变量的唯一权威字段，**必须存在于 tasks 表**，不得只依赖
  `task_attempts.attempt_no` 的聚合查询。首次 Claim 前为 0。
- `tasks.hotfix` 为布尔值，默认 false；§21 的 hotfix 抢占配额（每 30 分钟最多 3 次）以该
  字段为唯一判据，禁止在 Merge Queue 内存态另存一份。
- attempt 预算人工覆盖的**唯一权威字段名是 `tasks.budget_override_by`**（人类身份）。
  §10 迁移表 guard 与 §28 不变量中出现的 `attempt_budget_override` 是同一概念的
  事件侧命名（写入 `task_decisions` 的覆盖记录），不是第二个 tasks 字段；冻结表按
  `budget_override_by` 登记。
- `tasks.attempt_no`、`tasks.hotfix`、`tasks.budget_override_by` 三者 NOT NULL 有默认值
  （0 / false / NULL），使 §11 的条件 UPDATE 可以在同一条语句内断言预算门禁。

## 9. 方案、任务和产出契约

Planner 输出：

~~~text
plans/plan-003/plan.md
plans/plan-003/tasks.yaml
~~~

方案批准前由机械校验器检查：

- cancelled 任务必须声明 downstream_policy：block、cancel 或 escalate；默认 block；
- 下游传播必须留下 task event，不允许直接改库；

- DAG 无环且可拓扑排序；
- 任务引用闭合；
- capability 已注册；
- exclusive_resources 必须来自资源注册表，且同一任务内不能重复；
- secret_refs 必须来自 secret 注册表，scope、用途和最小权限必须匹配；
- glob 使用 POSIX 分隔符、小写、去重和规范化；
- outputs 和 consumes 的 name、type、schema_version 可以匹配；计划期只校验契约闭合，不要求尚不存在的实际 hash；
- acceptance 有明确 check；
- evidence source 来自已注册能力；
- evidence source 能产生判据要求的证据形态；
- verify profile 来自仓库侧 policy allowlist；
- budget、risk 和预计时长齐全；
- 计划任务数量、acceptance 数量、预算和路径覆盖不超过上限；
- 方案版本可产生不可变 plan snapshot。

**任务接替关系（`supersedes`）**：任务规格里可以带一个**可选**的 `supersedes`
（这条任务接替了哪一条 task_id）。改派（取消旧任务、按同样规格派一条新的）由派单方
声明它，平台机械校验三件事：旧任务**存在**、**在同一个群**、且处于**工作没有交付**的
状态（`cancelled` / `abandoned` / `stale` / `changes_requested`）——**还在跑的活不能被
接替**，那会变成两个主人。

- 链接只挂在**新**任务上：终态任务的行不被改写（改它就是改历史）。"这条活被谁接替
  了"由消费方在任务列表里反查；
- 它是**加法**：老读者忽略这个键即可，所以 `plan_version` 仍是 `v1`，**不需要提升
  `schema_version`**（§37.7 的提升规则只针对**新增事件**）；
- 不新增事件名、状态、状态迁移边；不新增 canonical 表与列。

计划规模上限必须配置。超限直接拒绝并要求 Planner 拆分，不能自动拆分后直接执行。

Planner 不应领取自己方案中的执行任务。确需领取时，必须披露并由人类确认。

awaiting_review | verify_code_failed | 兼容旧 worker：receipt 无效、differential 不成立或测试断言失败 | changes_requested

硬规则：

- 运行中的 owner 状态（claimed、in_progress、needs_help、blocked、plan_drift、impl_drift）必须有不依赖 owner 存活的 Lease 过期出口；
- queued 没有 owner、attempt 或 Lease；只记录 queue_reason=resource、worktree_capacity 或 merge_capacity；Verify 槽位不在 Claim 事务中预占，verify 背压只发生在 verify_jobs 层，路径冲突不创建 queued；
- verifying 由 Verify Worker 持有独立 verify Lease；代码失败回 changes_requested，环境失败原地重排同一 attempt，worker 崩溃只原地重排，执行超时才进入 escalated；verifying 不得经 queued 回到 claimed；failure_reason 必须区分 code_failed、env_failed、timeout、aborted；
- revert recovery 是 integration_health 的独立恢复状态机，不受普通 merge_start 的 green guard 阻塞；
- awaiting_review、approved、merging 由独立 review/merge worker 持有 Lease，不再使用开发 Harness 的 Lease；
- changes_requested 由返工巡检器管理，超时进入 escalated，重新提交前必须重新 Claim、创建新 attempt、获取开发 Lease；
- awaiting_human 和 escalated 由等待巡检器、提醒和人工待办管理；进入 awaiting_human 时暂停 owner Lease，resume 时重新签发 Lease；
- blocked 的依赖、资源和外部条件必须由独立巡检器检测，条件释放时走 unblock；
- 未定义迁移必须拒绝；
- 每个迁移必须有 guard、操作者、事件和副作用；
- R10 自环边完整清单（共 **10 条**）。R9 的 R9-10 只登记 5 条，遗漏
  `review_lease_expire`、`merge_lease_expire` 与 `needs_help` 的三条 help 边；R10-fix
  补齐为：
  - owner/verify 侧 5 条：`verifying | verify_env_failed`、

R8 状态机硬规则补充：

- `parent_task_id` 语义为父任务依赖子任务；不得用方向相反的隐含 child→parent 表示等待关系。
- 每个持有独立 Lease 的等待状态必须有对应 `lease_expire` 出口；`verifying` 的 job 状态变化不算任务进展。
- `ready_waiting_deps` 不参与 aging；只接受 `dependencies_satisfied`、`block_timeout` 和孤儿检测。
- `queue_reason` 仅允许 `resource`、`worktree_capacity`、`merge_capacity`；`verify_capacity` 只存在于 `verify_jobs`，不得写入 tasks。
- `verify_queue_timeout` 只由 verify queue 巡检器触发；queued verify job 只登记 `required_resources`，不持有 exclusive resource lease。
- drift 检测覆盖 claimed、in_progress、changes_requested、verifying、awaiting_review、approved、merging。

- 状态闭环检查属于阶段 0 验收：检查每个非终态至少有一条出边、每个状态从 draft 可达、merged 从 draft 可达、事件名在 allowlist 中唯一、每条边声明 side effect；DOC-STATE-001 必须覆盖可达性，并验证 needs_help、blocked 的入口边。

## 11. Claim、批量 Claim 和幂等

Claim 检查：

1. 任务为 ready，或是 changes_requested/plan_drift/impl_drift 的合法返工 Claim；
2. 所有依赖上游任务已经 merged；计划期只校验 consumes 的 name/type/schema_version 契约闭合，运行期再校验上游 task_outputs 的实际 hash 存在且 schema_version 兼容；approved 不算依赖满足；
3. 没有有效 owner 和 Lease；
4. 首次 Claim 在同一事务中冻结 integration HEAD 为 task.base_commit 并写 base_locked_seq；返工和重试必须复用该 base_commit，禁止现算 merge-base；
5. Harness 能力和质量门控满足；
6. exclusive_resources 可预占；exclusive_paths 只用于计划期排序、告警和 path_conflicts 巡检，不阻塞 Claim；
7. 并发窗口未满；
8. 任务版本没有漂移；
9. secret_refs 已登记且调用身份有最小权限。

已有任务的 Claim 还必须验证 base_commit 非空，并且是当前 integration HEAD 的显式祖先；首次 Claim 在同一事务中捕获当前 HEAD。base_commit 只允许在首次 Claim 写入，绝不因集成分支前进而更新。

worktree、端口、数据库、GPU、浏览器 profile 等资源必须在同一 Claim 事务中预占。预占失败时只进入 queued，不写 owner、attempt、Lease 或开发副作用。

claim_request_id 必须唯一。重复 request_id 返回第一次的完整结果，不得重复领取；同一 request_id 但 task_ids、参数或 payload_hash 不同必须拒绝并写入幂等冲突事件。

批量 Claim 默认 all-or-nothing。显式允许部分成功时，每项独立返回结果并写事件。
claim_request_id 只标识一次批量请求，但幂等记录必须按 claim_request_id + task_id 建立。重复提交同一批次时，返回每个任务项的首次结果；客户端可以使用新的 request_id 只重试失败项。

Claim 成功必须在同一事务中记录（queued 不记录以下 owner 字段）：

- owner；
- claimed_at；
- lease_until；
- claim batch；
- attempt_id；
- fencing epoch；
- task claim；
- task event；
- message delivery；
- side effect intent。



### R8 Claim 事务约束

Claim 路径必须使用 SQLite `BEGIN IMMEDIATE` 写事务，或由调度器单写者 goroutine
串行化；不得使用默认 DEFERRED 事务完成 Claim。事务内按以下顺序执行：读取并锁定
`claim_requests`、校验 payload hash、检查任务状态和 attempt 预算、预占资源、冻结
`base_commit/base_locked_seq`、递增 `current_epoch`、写 owner/attempt/Lease 和事件。

状态迁移必须是条件更新并断言 `RowsAffected == 1`：

```sql
UPDATE tasks
SET status='claimed', owner=?, current_attempt_id=?, current_epoch=current_epoch+1,
    state_changed_seq=?
WHERE task_id=? AND status='ready' AND current_attempt_id IS NULL
  AND (attempt_no < max_attempts OR budget_override_by IS NOT NULL);
```

任一步骤失败必须回滚；同一 `claim_request_id` 只返回首次结果。请求级幂等由
`claim_requests(claim_request_id PRIMARY KEY, payload_hash, task_ids_json,
partial_allowed, first_result_json, created_seq)`保证；payload、task 集合或参数不一致
必须写 `idempotency_conflict` 并拒绝整个请求。批量 `partial_allowed` 必须落库，默认
false。`CORE-CLAIM-002` 使用两个真实 SQLite 连接并发抢同一任务，断言只有一个 owner、
一个 attempt 和一条有效开发 Lease。

两层幂等的职责划分（`claim_requests` 是每请求一行，不含 `task_id` 列）：请求级的
"这次请求的首次结果"落 `claim_requests.first_result_json`；**per-task 的首次结果**按
`task_claims` 的 `unique(claim_request_id, task_id)` 落地，重试时以
`SELECT * FROM task_claims WHERE claim_request_id = ?` 逐任务项回放，不从 JSON 里反解。
批量 Claim 的每个任务项都必须留下一行 `task_claims`，失败项同样留行并带释放原因。

## 12. Attempt 和命令幂等

attempt 是任务的一次完整执行周期，至少覆盖：

~~~text
claim → worktree → work → submit → verify → review → merge
~~~

以下事件创建新 attempt：

- 首次领取；
- stale 后接手；
- changes_requested 后重新 Claim 并重新提交；
- verifying 失败后的新 attempt；
- 人类批准重开；
- 任务 split 后产生新子任务；子任务 ID 为 parent-id.s<ordinal>，继承 plan snapshot、未使用预算和 review policy，attempt 从 0 开始，父子依赖边写入 task_dependencies。

命令幂等键必须包含操作语义：

~~~text
claim: claim_request_id + task_id（批量请求按任务项分别幂等）
submit: task_id + attempt_id + completion_revision
verify: task_id + attempt_id + verify_profile + commit + job_id
review: task_id + attempt_id + reviewer_id + review_revision + reviewed_commit
merge: task_id + attempt_id + merge_target + merge_revision
publish: task_id + attempt_id + commit + fencing_epoch + idempotency_key
receipt: task_id + attempt_id + commit + verify_profile
~~~

不能只用 task_id 作为 completion 或 submit 的唯一键，否则返工后新提交会被旧记录挡回。

## 13. Lease、Heartbeat 和 fencing

默认参数：

- Lease：15 分钟；
- Heartbeat：5 分钟；
- Stale grace：连续 3 次无心跳；
- max_attempts：3；
- max_review_rounds：2；
- stuck 检测：连续 3 次巡检无进展触发 stuck_threshold_reached→escalated，连续 5 次触发 stuck_human_threshold→awaiting_human；
- verify 最大 attempt：2；
- 零 commit：连续 2 个 heartbeat 窗口无新 commit 时告警；
- 续期被拒：立即视为失联；
- awaiting_human 提醒：默认 30 分钟，退避重复提醒；
- 人类等待超时不自动放行、不自动取消；
- submit_result 成功后立即释放开发 Harness 的 owner Lease；
- awaiting_review 由 review worker 获得独立 review Lease；
- approved/merging 由 merge worker 获得独立 merge Lease；
- review/merge 等待超时只进入 escalated 并告警，不重新抢占已经提交的开发任务。

Lease 使用双锚点：

~~~text
grant_wall + grant_mono + boot_id

boot_id 相同：使用单调时间差
boot_id 不同：使用墙钟并执行一次重启豁免
~~~

事件排序使用全局 seq，时间戳仅用于展示。

每次 Claim 或 reclaim 生成递增 fencing epoch。旧 epoch 的写入、push 和 merge 必须拒绝。
approved 状态必须冻结 agent 分支：Push Proxy 写入 refs/meta/approved-commit 和冻结标记，Harness 对该分支的 push 一律拒绝；只有 human.adjudicate 退回 changes_requested 或 Merge Worker 的 revert recovery 可以解除相应冻结。Lease 计时以调度器收包时间为准，忽略 Harness 上报时间。
首次 Claim 生成不可变 base_commit=当时 integration HEAD 和 base_locked_seq；后续 attempt 永远复用这两个字段，禁止重算 merge-base。

canonical Git 拓扑和权限：
- canonical 是由调度中心账户拥有的 bare repository；
- Harness 账户对 canonical 的 refs、objects、config、hooks 和裸仓库文件系统没有写权限，Windows ACL 必须明确拒绝；
- Harness 只能通过 Push Proxy 发布自己的 agent 分支，integration/main 只能由 Push Proxy 或 Merge Worker 写入；
- agent worktree 使用其账户拥有的独立可写 gitdir 和工作树，gitdir 不得位于 canonical bare repository/worktrees；objects 通过 file:// alternates 只读指向 canonical；worktree_add intent 由调度中心创建并设置 ACL；任务分支的发布仍须由服务端校验 task_id、attempt_id、commit 和 fencing epoch；
- canonical bare repository、state.db、WAL/SHM 和事件 JSONL 都属于备份集。

fencing 必须有实际执行点：
- Push Proxy 在 push 前校验 task_id、attempt_id、commit、当前 fencing epoch、目标分支和调用身份；
- pre-receive hook 可再次拒绝旧 epoch，但 hook 不能把 state.db 当作共享可写依赖；
- Harness 账户执行 git update-ref、直接修改 refs/objects/config/hooks 或直接 push integration/main 必须被 OS ACL 或服务端拒绝；
- 任何绕过 Push Proxy 的写入都必须产生拒绝审计事件。



### R8 发布对象传输与账户边界（ADR-059）

Harness 永远不执行 `git push` 到 canonical，也不把 Harness gitdir 作为 Git receive
端。宿主模式为 `patch_apply` 时，Harness 改为上传 patch 到 `artifacts`，调度中心
在 attempt 临时对象库 apply 并生成归属于该 attempt 的新 commit；此时 `head_commit`
来自调度中心生成的 commit，`side_effect_intents(type=patch_apply)` 必须记录
`patch_hash`、`applied_by`、`generated_commit` 和当前 fencing epoch，后续 Verify、
receipt、fencing 与 Merge Gate 与 `native_cli` 完全一致。Harness 只调用 REST `publish_task_branch`。调度中心账户对对应 Harness gitdir
拥有只读 ACL，对 canonical bare、refs、objects、config、hooks 拥有写权限；Harness
账户对 canonical 和调度器 state.db 拒绝写入。Push Proxy 是调度中心内部组件，不是
`pre-receive` 接收端。

发布流程必须通过 `side_effect_intents(type=push)`：

1. 校验 task、attempt、fencing epoch、branch 命名、commit 可达性、当前 head 和
   idempotency key；校验 `.git/objects/info/alternates` 只能指向该项目 canonical
   objects，拒绝任意外部路径；
2. 调度中心以自身账户从 Harness gitdir 执行等价
   `git fetch <validated-agent-gitdir> <commit>`，或使用受控 bundle/pack 传输，
   将对象导入 canonical；Harness gitdir 不可写 canonical；
3. 校验对象导入后的 commit tree、父链和 attempt 元数据，再执行 `update-ref`；
4. 写入 `refs/meta/approved-commit`、发布 receipt、intent 完成事件和审计记录。

旧 epoch、错误 alternates、不可达 commit、非任务分支或重复 intent 必须拒绝，且不
得产生 canonical ref 写入。删除所有把本地文件 fetch 描述为 `pre-receive hook` 的
依赖；本地 fetch 由 Push Proxy 的服务端校验实现 fencing。

默认 Windows 账户布局：`agent-scheduler` 拥有 state.db/canonical/凭证目录，
`agent-harness-<id>` 拥有自己的 worktree/gitdir，`agent-verify` 只读 canonical
并只能写 verify overlay。凭据由 Windows Credential Manager 管理。`--insecure-single-account`
仅允许阶段 0/1 的功能开发，不能满足阶段 2 ACL 退出条件。

## 14. Worktree、路径和资源

每个任务独立 worktree 和分支：

~~~text
agent/<group-short>/<harness>/<task-id>/<attempt-id>
~~~

物理目录使用短 ID，例如 wt/a3f9。完整分支名保存在数据库。Windows 启用 Git longpaths。

分支名与 worktree 目录一一对应。R9 统一命名口径为
`agent/<group-short>/<harness>/<task-id>/<attempt-id>`，help 分支与 help worktree 为
`agent/<group-short>/<harness>/<task-id>/help-<n>`；§17 权限矩阵、ACL 校验脚本与
Push Proxy 的分支白名单必须采用同一口径，阶段 0a 冻结。

Worktree 生命周期管理：
- 协作者 help worktree 使用独立 help-<n> 分支和 Lease，计入 concurrent_worktree 上限；协作者产出必须作为 artifact 进入 owner attempt 的证据链，但不改变 owner completion；协作者产出需单独 review 后才能被 owner 合并；
- merged、abandoned、cancelled 后进入 pending_archive；
- changes_requested 返工必须先冻结旧 attempt，旧 worktree 进入 pending_archive，再为新 attempt provision 新 worktree；新 worktree 必须 rebase 到当前 integration HEAD；base_commit 仍只作为 differential 锚点保留，rebase 后 head_commit 变化必须重新 verify/review；不得让两个 attempt 共享可写目录；
- 归档包含 git bundle、patch、logs 和 receipt；
- 归档校验通过后才回收 worktree；
- verify job 成功且 receipt 落库后立即回收该 job overlay；失败 job 的 overlay 保留 7 天或直到磁盘告警，先到者为准；Verify Worker 崩溃重排时，新 job 创建后立即回收旧 job overlay；
- 磁盘告警清理优先级：已成功且 receipt 落库的 overlay、失败超过 3 天的 overlay、已归档的 merged/abandoned/cancelled worktree、最后才是失败未满 3 天的 overlay；
- 并发 worktree 默认上限 8，超限时任务进入 queued，并写 queue_reason=worktree_capacity；
- per-profile 共享依赖缓存使用只读缓存加可写 overlay。

每条 resource_leases 记录必须包含：
- resource_id；
- lease_until；
- acquired_by_attempt；
- acquired_by_epoch；
- released_by；
- released_at；
- release_reason。

资源巡检器必须回收过期资源。abandon、reclaim、submit_result 和 merge 结束时按 attempt 释放关联资源，并写 resource_lease_released 事件。

资源包括：

- 文件路径；
- port；
- 数据库；
- 浏览器 profile；
- GPU；
- package-lock、go.sum、Cargo.lock 等锁文件；
- 远程机器和 Worker。

exclusive_paths 重叠时在 Planner 阶段自动生成依赖或排序约束，不使用永久硬锁。DAG 必须检测环。
运行期 path_conflicts 巡检器只检测 active 任务的重叠路径，写 path_conflict_detected 告警并降低优先级；不创建 queued、不持有永久路径 Lease。

锁文件变化的处理必须区分：
- Planner 或 Harness 对锁文件的真实提交修改：使相关 verify receipt 失效并重新验证；
- verify profile 产生的测试副产物：只写入 overlay，不修改任务 worktree；
- policy 中标记 lockfile_mutating 的 profile：必须在 overlay 中解析依赖，不能回写工作树，避免验证震荡。

## 15. 事件、事实源和 Outbox

系统必须选择唯一的事实事件源。建议采用：

- SQLite 事件表作为本地事实源；
- 每个事件带全局 seq 和 schema_version；
- JSONL 作为轮转备份、导出和灾备；
- SQLite 投影只能由事实事件重建；
- 不允许 SQLite 和 JSONL 各自独立写事实。
- JSONL 由 SQLite 提交成功后的异步 exporter 生成，不参与事务双写；
- jsonl_exports 记录 stream、exported_seq、file_hash、status、attempts、last_error 和 updated_at；
- exporter 从 exported_seq+1 顺序读取事件，写入临时文件后 fsync、原子 rename，再推进 exported_seq；
- 导出失败进入重试队列，重启和定时巡检比较 SQLite max(seq) 与 exported_seq，自动补导并告警；恢复时以 seq 去重，禁止制造空洞或重复事实事件。

所有 Git、进程、worktree、merge、push、归档和删除副作用通过 side_effect_intents：

~~~text
intent_id
task_id
type: worktree_add | merge | revert_merge | push | archive | verify_run | patch_apply
idempotency_key
status: pending | done | failed | unknown
job_id
pid
pgid
boot_id
created_seq
~~~

重启流程：

0. 获取 scheduler_lock 后进入 drain 窗口；先对账 intents、探测 Harness 存活和心跳，不立即执行 Lease 过期扫描；停机时间超过 lease_ttl 时至少等待两个 heartbeat 周期。
1. 获取 scheduler_lock；
2. 扫描 pending 和 unknown intent；
3. 探测目录、分支、commit 和远程 refs；verify_run 按 job_id、pid、pgid、boot_id 对账，Windows 用 Job Object 归组并清理孤儿；重试必须使用新 job_id 和独立 overlay；
4. 补齐或标记失败；
5. 写 intent_reconciled 事件；
6. 重建查询投影；
7. 恢复调度循环。drain 窗口结束仍无心跳的任务才写 `scheduler_restart_lease_expiry` 并进入 stale；boot_id 变化只豁免一次 wall/mono 换算，不豁免 `lease_until` 到期。

## 16. 完成证据和 Verify

Markdown 是可读视图和交接材料，不是权威状态和 receipt。

每个任务至少生成：

~~~text
task.md
status.md
completion.md
test-results.md
handoff.md
verification/receipt.json
reviews/
~~~

完成提交必须包括：

- 精确 commit；
- 修改文件；
- 测试命令和结果；
- 已知问题；
- 交接建议；
- task_id；
- attempt_id；
- fencing epoch。

Verify 与 Review 串行：submit_result 先进入 verifying，Verify Worker 必须先产生通过 receipt，之后 Reviewer 才能 claim awaiting_review。Review 不能消费 failed、timeout 或不匹配 commit 的 receipt。

Verify 必须针对要合并的精确 commit，在全新 detached worktree 中执行，并执行 baseline differential：

1. 在 base_commit 的全新 detached worktree 执行 verify_cmd，必须非 0 退出；
2. 在 head_commit 的全新 detached worktree 执行 verify_cmd，必须 0 退出；
3. 记录 diff 中新增的测试文件 new_test_files；
4. 任一步骤不满足，receipt 无效并回到 changes_requested；
5. 纯重构、纯文档或删除类任务可以声明 differential: not_applicable，但必须附理由、进入 awaiting_human 并由人类确认。

Verify 环境必须满足：

- git status 必须为空；
- 使用冷构建或明确的干净缓存；
- 不挂 state.db；
- 不注入 Git 凭据、调度器凭据和未在 verify profile 中声明的 secret；允许注入的 secret 必须同时出现在 task.secret_refs 与 profile allowlist 中；
- 低权限隔离；
- 网络白名单；
- canonical bare repository 的 objects、refs、config、hooks 对 Verify 账户拒绝写入；
- checkout 使用独立 per-worktree gitdir，只有 HEAD、logs、index 等管理文件位于可写 overlay；
- 测试产生的文件只能写入独立 overlay；
- Verify 账户必须能完成正常 checkout 和 git status，但尝试写 .git/config、hooks、refs、objects 必须被 ACL 拒绝。

verify 命令根必须来自仓库侧人类维护的 policy allowlist。Planner 只能填写允许的参数和测试路径。

receipt 权威副本只能在调度器数据库中，Harness 和仓库副本均不可写；仓库副本只是带 hash 的只读视图。verification_receipts 只允许 append，禁止 UPDATE/DELETE，唯一键为 (task_id, attempt_id, commit, verify_profile)。同一 attempt 的重复 receipt 返回首次结果；不同 commit 必须生成独立 receipt，Merge Gate 只认精确匹配待合并 commit 的那一份。
receipt 至少记录：

- commit；
- base_commit；
- baseline_exit_code；
- head_exit_code；
- new_test_files；
- differential_mode；
- diff hash；
- 测试退出码；
- verify profile；
- verify_env_hash；
- 工具链版本；
- fencing epoch；
- task_id、attempt_id、receipt_id；
- 输入的 task_decision 列表；
- injected_secret_ids 和 secret_versions（只记录标识与版本，不记录秘密值）；
- failure_reason（code_failed、env_failed、timeout 或 aborted）；
- failed_test_cases（指向 test_case_results.result_id）；
- flaky_registry_ids；
- diff_intersection（失败用例与 diff/new_test_files 的交集结果）。

judge 类型 acceptance 不能单独让任务进入 awaiting_review。
judge 只能用于辅助分析，不得作为门禁性 acceptance。门禁项只允许 cmd 或 human。
judge 输入严格限定为 task diff 和 acceptance 文本，不得包含群聊、其他 Agent 的 completion.md 或其他 untrusted 内容。
judge receipt 必须记录 model、prompt_hash、完整输入输出和理由；同一 judge 不得连续两次审查同一任务。judge 结果只能触发 changes_requested 或供 Reviewer 参考，不能单独产生 approved。

Verify 由独立 Verify Worker 池执行。verify_jobs 至少包含：

~~~text
job_id
task_id
attempt_id
fencing_epoch
verify_profile
status: queued | running | passed | failed | timeout | aborted
failure_reason: null | code_failed | env_failed | timeout | aborted
lease_until
worker_id
boot_id
resource_requirements
baseline_exit_code
head_exit_code
receipt_hash
receipt_id
created_seq
updated_seq
~~~

Verify Worker 必须注册资源能力并持有独立 Lease。默认参数：

- verify Lease：30 分钟；
- verify Heartbeat：5 分钟；
- verify job 排队等待 SLA：30 分钟；
- concurrent_verify：3；
- Verify Worker 崩溃：保持 verifying 和原 attempt，经 verify_run intent 对账确认进程已死后，创建新 verify_job、job_id 和 overlay 原地重排；verify 幂等键包含 job_id，因此新 job 不会复用旧 env_failed 结果；不回 queued、不新建 attempt、不重新开发；
- Verify 执行超时：failure_reason=timeout，进入 escalated 并通知人类；Lease 到期且进程已死则按 verify_lease_expire 原地重排；环境失败连续达到 max_verify_env_retries=2 才 escalated；
- review Lease：20 分钟；merge Lease：30 分钟；Review/Merge Heartbeat：5 分钟；
- 每个 verify job 使用 job_id 独占 overlay，重试不得复用旧 overlay；
- CPU、内存、磁盘和网络白名单属于 resource_requirements。

## 17. 安全、秘密和权限

阶段一必须具备安全七件套：

1. 非管理员账户运行 Harness；
2. 工作目录白名单；
3. Harness 禁止写主分支；
4. 外部 Agent 内容标记为 untrusted；
5. secret 出口扫描；
6. 副作用分级；
7. Verify 隔离执行。

副作用分为：

- read_only；
- retryable_write；
- irreversible_write。

不可逆操作默认 dry-run 或进入 awaiting_human。

Secret 扫描必须覆盖（顺序是先扫描、后落库）：

- artifact 和 completion 写入；
- task event 和消息写入；
- git staging、commit 和 push；
- Merge Gate 最终检查。

API 接收 completion、artifact、消息、mention、event 正文时先做出口扫描；命中后拒绝落库，只记录不含秘密值的 `secret_scan_blocked` 事件（位置、规则、值 hash）。通过扫描后才可写入 task_events/task_messages。若已落库内容后来被判定为敏感，Merge Worker 或人类可调用 schema 级 `task_events.redact(seq, reason)`，投影重建使用 redacted 值，原始字节只保存在加密隔离归档中。任一阶段发现 secret 都必须阻止后续合并并写入安全事件。

Secret 要求：

- 不写入任务文档、聊天和事件；
- 只通过短时凭据或受控环境变量注入；
- 记录访问主体、时间、任务和用途；
- 默认不允许 Harness 读取其他任务的 secret；
- secret 访问不能由 Agent 自己批准。

权限角色：

- 人类管理员；
- 项目负责人；
- Planner；
- 开发 Harness；
- 协作者；
协作者只能读取所属任务上下文，默认不能读取 secret；help artifact 的 commit、review 和归属必须可追溯。
- Reviewer；
- Merge Worker。

## 18. 人类决策和 pinned 决策

需要人类判断时进入 awaiting_human，必须创建 task_decisions；split_task 的父子关系、预算和依赖也必须写入 task_decisions 或 task_events：

~~~text
decision_id
task_id
attempt_id
actor
question
options
answer
decided_seq
scope
expires_at
superseded_by
~~~

人类等待规则：

- 默认 30 分钟提醒；
- 退避式重复提醒；
- 超时不自动放行；
- 每条问题必须有结构化摘要；
- 决策随 read_context 下发；
- 决策进入 verify receipt 的输入清单。

in_progress 可以通过 human.question 进入 awaiting_human，处理后可以回到 in_progress、ready 或 cancelled。进入 awaiting_human 时暂停 owner Lease 计时，human.resume 时重新签发 Lease；未授权任务只返回计数和脱敏标题。

pinned 决策是高影响上下文：

- pin 和 unpin 只接受人类 token；
- Harness token 调用返回 403 并写事件；
- Agent 提出的内容必须先作为普通消息；
- 人类 pin 后才能进入长期上下文；
- 即使人类 pin，Agent 来源仍保留 untrusted 标记；
- pin 变化必须写审计事件。

## 19. 群聊和上下文

消息支持：

- 人类、Harness、调度器和系统消息；
- Planner 和 Reviewer 的 API 动作与 Lease 事件；
- @mention；
- 任务、方案、文件和审查引用；
- 帮助、接受、拒绝和交接；
- **有窗口中途加入项目**（`add-member` 签名）：办公室加人时带上它（含
  `add-member-json:<harness_id>`）；管理员据此**知道**（在群里说一声），并把**还没人
  领的活**改派给新来的窗口；已经在跑的活不换人（换人是人按条决定的）。
- **成员提「目标要改」**（`goal-change` 签名）：目标是群主的，成员只能**提**。
  管理员听见之后把原话带给群主（群里是群主读的地方），**自己不**改目标；群主的
  回答随后被管理员用来重新细化，方案随之修订。成员的其他消息只记在运行日志里，
  不惊动任何人（逐条回应是要花钱的）；
- 未读和已读；
- Markdown、代码、日志和文件链接。

**定向消息（只给两端看）**：

- 一条带 `direct` 签名的群消息：收件人就是 mentions 里的那些窗口；
- 读路径按身份过滤：只有发送方与收件方看得到，其他成员看不到；
- 无法识别身份的读者看不到定向消息（失败关闭）；
- 投递记录与 mention 共用一张表（`message_deliveries`），不另建一套；
- 不进任务的上下文（成员读任务上下文时看不到它）；
- 不新增事件名、状态或迁移边：`direct` 只是一个消息签名（refs 里的一个串），
  `schema_version` 因此不动（§37.7 的提升规则只针对新增事件）。

**管理员回私聊**：

- 管理员 harness 收到一条定向消息后，**用它自己的模型通道作答**，答案作为一条新的
  定向消息发回（收件人 = 原发件人）——仍然只是 §19 的消息，不新增事件名或状态；
- 给模型的只有平台自己的任务账本（任务 id、标题、状态、执行者、最近一次失败原因）；
  账本里没有的东西必须直说“不知道”，不许编原因、编数字；
- 模型通道失败时，管理员发一条定向消息明说“没答上来 + 原因”，**不发**一条看起来像
  回答的空话，也不把这条私聊混进群回执；
- 私聊内容**不进群**：定向消息不会被当成群主对目标的回答去再细化（那会把私聊写进
  整群可见的回执里）。

调度器为每个任务生成上下文视图：

- plan snapshot；
- 当前状态；
- pinned 决策；
- 最近 N 条消息；
- 相关事件；
- 未读 mention；
- 当前 attempt；
- 当前 receipt 和 review 摘要。

read_context 支持 since_seq 增量读取，并受 context_budget 限制，默认 50k tokens：
- pinned 决策和未读 mention 全量返回；
- 剩余 budget = max(0, context_budget - pinned_tokens - mention_tokens - 事件聚合 tokens)；预算不足时优先返回 pinned 摘要和 mention 元数据，不返回正文；每条消息按 500 tokens 估算，返回 min(20, floor(剩余 budget / 500)) 条；
- 剩余 budget < 500 时不返回消息正文，只返回计数和 fetch_detail(seq_range)；
- 摘要本身计入 budget，并标记为 untrusted；
- 提供 fetch_detail(seq) 获取完整详情。离线 Harness 重新上线时，重要 mention 必须重新投递并记录 delivered、read 和 retry。

Agent 生成的摘要属于 untrusted 内容，不能替代原始事件和权威状态。

## 20. 调度、公平和质量

普通低风险任务允许自助 Claim。高风险任务使用指派或人类确认。

调度策略：

- priority + aging；
- Harness 质量分；
- 饥饿告警；
- concurrent_claim；
- concurrent_review；
- concurrent_verify；
- concurrent_worktree；
- 重试、预算和时间熔断；
- escalated 状态。

质量分可以参考通过率、返工率、stale 率、卡住率和成本效率，但不能修改历史证据。

ready 持续超过 expected_duration 的配置倍数无人领取时，进入 escalated。

超预算、超重试、超时或连续失败时进入 escalated，不自动偷偷降级模型。

## 21. Review 和 Merge Gate

Review 和 Merge 本身也是带 Lease、attempt、stuck 检测和事件的任务。

Planner、Reviewer 和 Git 发布动作必须有明确 API：

~~~text
planner.create_plan(plan_id, plan_snapshot, idempotency_key)
planner.validate_plan(plan_id, plan_hash)
planner.submit_plan(plan_id, plan_hash)
review.claim(review_id, attempt_id, reviewer_harness_id)
review.submit(review_id, reviewed_commit, verdict, findings, evidence_hash, review_revision, idempotency_key)
git.publish_task_branch(task_id, attempt_id, commit, fencing_epoch)
~~~

Planner 只能创建和提交方案草稿，批准仍是人类动作；Planner Lease、Reviewer Lease 和幂等键都必须写入事件。reviews 记录至少包含 review_id、task_id、attempt_id、reviewer_harness_id、reviewer_provider、status、lease_until、fencing_epoch、reviewed_commit、verdict、findings_hash、review_revision、created_seq、completed_seq。

流程：

~~~text
awaiting_review
→ approved
→ merging
→ 集成分支
→ 全量测试
→ merged
~~~

Merge Queue 必须验证：

- plan snapshot 和 plan hash；
- task commit；
- receipt；
- fencing epoch；
- required reviews；
- 高优先级未解决意见；
- 集成测试；
- side_effect_intent；
- secret 扫描结果，且扫描没有阻断项；
- 目标分支最新基线；
- Push Proxy 已验证 fencing epoch；
- receipt.commit == 待合并 commit == 任务分支当前 head；
- review.reviewed_commit == 待合并 commit；
- receipt.fencing_epoch == task 当前 epoch；
- receipt.base_commit == task.base_commit；
- receipt 只能 append，禁止用新 commit 覆盖旧 receipt；
- Push Proxy 发现同一 attempt 的 commit 未被已通过 receipt/review 覆盖时，必须要求新的 verify 和 review；
- task.base_commit == receipt.base_commit；
- approved 后分支头若前移，调度器自动触发 reopen_for_changes、解冻分支并回 changes_requested；不得只在 Merge Gate 做事后拒绝；必须重新 verify 和 review。

合并失败回到 approved 或 changes_requested。Hotfix 可以抢占队列位置，但不能跳过任何 gate。

集成测试采用全局健康位、基线、用例级归因和有限重试：
- 合并前对当前 integration commit 执行 baseline_receipt，并把结果写入 integration_health；
- baseline 任何门禁用例失败时，integration_health=red，Merge Queue 立即 stop-the-line，暂停所有新 merge，包括 hotfix；除下述 revert recovery 外，只有进入 awaiting_human 的结构化人工覆盖才能例外；
- 合并后失败时，调度器先停止队列、记录失败用例和 diff 交集；若判定为本次变更引入，Merge Worker 通过专用 revert recovery 状态机生成并发布 revert merge commit。该操作是唯一的 green guard 豁免，只撤销已记录的失败 merge commit，不发布新功能；必须机械断言 tree(revert_commit) == tree(first_parent(failed_merge_commit))，且 revert_commit 的历史只包含 failed_merge_commit 加该 revert commit；任一断言失败则 revert 无效并进入 escalated。随后必须写 merge_reverted 事件和 revert receipt，立即重跑集成测试；未恢复 green 则进入 escalated，禁止自动重试。原任务回 changes_requested；不得 reset 或继续在红基线上排队；
- “基线也失败所以不阻断”仅适用于已登记的 flaky 任务、同一 test_case_results.test_name 在 baseline_receipt 和 head receipt 中均失败、failed_test_cases 已列出、flaky_registry_ids 已登记，且 diff_intersection=false；每个失败用例必须完成 flaky registry 比对和测试文件/调用代码与 diff 的静态交集检查；缺任何字段都必须阻断合并；
- 同一 commit 只允许一次自动重跑；再次失败仍保持 integration_health=red，创建 flaky 任务并停止队列；
- integration_health 恢复为 green 后才允许 Merge Queue 继续；revert recovery 必须有 revert receipt、审计事件和集成复跑记录；禁止人工绕过 gate，绕过请求必须进入 awaiting_human 并记录事件。

集成健康状态机独立于任务状态机：

~~~text
green | merge_failure_detected | 当前 merge 失败 | red
red | start_revert | Merge Worker、失败 commit、revert receipt 已登记 | reverting
reverting | revert_published | revert commit 经 Push Proxy 验证 | retesting
retesting | integration_green | 集成复跑通过 | green
retesting | integration_red | 集成复跑仍失败 | escalated
~~~

start_revert 是唯一允许在 integration_health=red 时执行的集成写入；它不使用普通 approved | merge_start，但必须校验 Merge Worker 身份、失败 commit、epoch、revert receipt 和审计事件。

Merge Queue 必须有容量和背压：

- 并发 verify 数量，初始上限 3；
- 并发 review 数量，初始上限 5；
- 并发 worktree 数量，初始上限 8；
- 最大队列长度和资源水位；
- 队列满时新任务进入 queued，不自动进入 escalated；
- verify 超时、失败或连续重试耗尽时才进入 escalated；
- 磁盘空间不足时停止新 worktree 和 verify 创建，并按 §14 的 overlay/worktree 清理优先级执行；
- 只读、可重试和不可逆副作用分别限流；
- hotfix 抢占配额默认每 30 分钟最多 3 次，超过后按普通队列等待；普通任务等待超阈值进入观测告警，不允许被 hotfix 无限挤压。

审查优先选择不同 Provider。相同 Provider 的两个 Reviewer 需要额外人类确认。



### R8 revert 影响分析

`start_revert` 前必须按 `task_dependencies` 的反向闭包计算被失败 merged 任务影响的
所有下游，覆盖 draft、draft_rejected、ready_waiting_deps、ready、queued、needs_help、
blocked、changes_requested、verifying、awaiting_review、approved、merging 以及已
merged 的下游，不允许只处理 merged、approved、awaiting_review 和 ready_waiting_deps
四类。
对每个下游写 `task_decisions` 与 `task_events(revert_impact_detected)`，设置
`tasks.upstream_invalidated_seq`，冻结该任务及其后续依赖的 Claim。已 merged 下游进入
`escalated` 或 `awaiting_human`；只有人类明确记录“不依赖该产出”才可恢复。下游不得
继续使用旧 `task_outputs.merged_seq` 作为依赖满足证据。§12 不变量：上游 merged 后
被 revert，所有下游必须重新评估，直至新的 receipt、output hash 和 Merge Gate 通过。

### 38.9 R10-fix-11：task_claims 的 attempt_id / owner 改为可空

**来源**：MVP-04（Qoder）在任务卡「已知问题」里提出规范冲突，要求裁定。

#### 冲突

三处规范此前无法同时满足：

| 出处 | 规定 |
|---|---|
| §11:511 | `ready / claim_deferred_resource` 预占资源失败时「只进入 queued，**不写 owner、attempt、Lease**」 |

MVP-04 用**空串哨兵**（`NO_ATTEMPT = ""`）绕过，但空串与「真实但异常的值」不可区分，
属于设计债 —— 任何 `WHERE attempt_id <> ''` 之类的判断都会踩坑。

#### 裁定：改 schema 让两列可空

三条路径里选了改 schema：

1. **改 R10 更差**：§11:511 与 §11:617 两条规则本身都合理，是 schema 与它们冲突。
   改规范等于为迁就实现而扭曲需求。
2. **继续用哨兵最差**：数据层无法区分「未领取」与「领取了但值异常」。
3. **改 schema 最干净**：「未领取」与「已领取」在数据层就区分开，不依赖应用层约定。

**兼容性已核实**：MVP-04 的重放逻辑用
`LEFT JOIN task_attempts ta ON ta.attempt_id = tc.attempt_id`，
`LEFT JOIN` 本就容忍 NULL，无需改动。

#### 落地

- 新增 `backend/migrations/002_task_claims_nullable.sql`：SQLite 不支持 `ALTER COLUMN`，

- `app/claim/service.py` 的 `NO_ATTEMPT` 由 `""` 改为 `None`；
- `test_claim.py` 的断言由 `== ""` 改为 `is None`，并补 `owner is None`；
- `test_database_events.py` 两处硬编码迁移数量（`== 1`、`== [0, 1]`）改为按目录里
  `.sql` 文件数与相对关系断言 —— 以后加迁移不必再改测试。

门禁 docstate 90/90、ruff check + format 全绿。

~~~

硬规则：

1. **硬门禁**：`allocation.opened` 要求绑定快照已完成 ≥1 轮传阅（存在 `completed` 的
   传阅轮）。未传阅不得分配 —— 这是拒绝，不是提醒。
2. **申请不等于领取**：`application.submitted` 不产生 owner、attempt、开发 Lease 或
   工作区；只有"已 `accepted` 的分配"才构成 §11 Claim 的授权，且 Claim 必须校验
   `harness_id`、`task_id`、计划版本、分配版本与 `expected_revision` 全部匹配。
   **强制范围（R10-fix-13 增补；群主 2026-10-17 裁定为"分群开关"）**：这一格按**群**
   强制，由 `AP_ALLOCATION_REQUIRED_GROUPS` 显式列出。列在其中的群，**第一份**
   attempt 必须有一份"已 `accepted` 且尚未被用掉"的分配作授权，且该分配所属轮绑定的
   方案快照必须等于任务当前的快照（即上面"计划版本"一格）；不满足则以
   `claim.not_authorized`（409）拒绝，不产生 attempt、Lease、工作区，也不改
   `tasks.status`。未列出的群维持既有行为：全局强制会让存量任务一次性全部不可领取，
   那等于换掉领取机制而不是把规则做实，限制范围因此是**显式配置**而非默认放宽。
   两处刻意收窄，均在此登记：
   - **只拦第一份 attempt**：`changes_requested` 的返工继续的是同一份已被授权的作业；
     若返工也要新分配，一次 verify 失败就会把任务钉在等分配上（本仓已踩过的死端形态）。
   - **"分配版本"（`expected_revision`）尚未强制**：§11 的 Claim 请求里没有这个字段，
     强制它需要给 `/adapter/claim` 加字段并让全部调用方带上，未落定为待办。
3. **回避**：管理员不得裁决自己参与竞争的任务；`decider_harness_id` 不得等于任何候选的
   `harness_id`。无其他无利益冲突的管理员时，交给群主处理。
4. **并发**：`(round_id, task_id)` 同一轮最多一条裁决，`expected_revision` 条件更新，
   两个管理员同时裁决只能一个成功；撤销与 Claim 并发只能一个成功。
5. **计划变更**：任务范围、验收或依赖变化时必须生成新快照与新分配轮次，旧申请与未执行
   授权失效；已执行任务走 §10 的漂移/回收路径，不静默取消 Lease。
6. **不改任务状态**：A 事件不写 `tasks.status`；分配结果只影响"谁有权 Claim"。
7. **群主保留最终控制**：可查看材料、接管管理员、取消尚未执行的分配、要求重新评选。

### 38.12 R10-fix-17：任务接替关系进平台字段

**来源**：办公室的「这条活的来路」——改派链此前只能在事件流里一条条读。

#### 缺口

改派 = 取消旧任务 + 按同样规格派一条新的（`cancel` + `dispatch` 两步既有动作）。
**"谁接替了谁"没有平台字段**：

- 旧任务的 `cancel` 事件带的是**理由**，没有"接替者"——派单发生在取消**之后**，
  那一刻新任务还不存在；
- 新任务的事件里也没有"接替了谁"；
- 于是消费方（办公室、以后的调度器）要还原接替链，只能去**读消息文本**
  （"管理员 Harness 改派：FD-x → FD-y"）——那不是平台事实，是一句话。

#### 修法

派单可以声明**可选**的 `supersedes`（§9），平台校验三件事（旧任务存在、同群、
工作没有交付），链接写进**新任务的计划快照**；任务列表与任务详情都投影它。

- **落在快照**而不是新表：快照是任务的**不可变契约**，而"这条任务接替那一条"就是
  契约的一部分（新的执行者在工单里读到它，接着上一个 attempt 的断点报告干）。
  新表要多一条 canonical 表，以及它的写入方与保留策略（R10 §8 / §37.6）。
- **方向只挂新任务**：终态任务的行不被改写——改它就是改历史。"这条活被谁接替了"
  由消费方在任务列表里反查。
- **加法**：老读者忽略这个键即可，`plan_version` 仍是 `v1`，**不提升
  `schema_version`**（§37.7 的提升规则只针对**新增事件**；本条不新增事件）。
- **幂等**：`supersedes` 进请求摘要，但**只在有值时**进——没有链接的请求必须与字段
  存在之前哈希完全一致，否则旧 `request_id` 的重放会变成"同 id 不同内容"的冲突。

### 38.13 R10-fix-18：用户与管理员之间没有可直达的私聊通道

**来源**：办公室的「与管理员对话」——用户想直接找管理员说事，只能在项目群里发消息，
而群消息是整群可见的：成员的任务上下文里会出现它（§19 的“最近 N 条消息”）。

#### 缺口

平台只有一种消息：群消息（`task_messages`）。

- 收件人只能靠 `@mention` 表达，**没有“这条只给某个人看”的表达**；
- `message_deliveries` 记着每条消息的收件人，但没人按它过滤读取；
- 于是“私聊”要么不存在，要么靠界面自己过滤（前端记得哪些 ref 是私的）——
  那是**界面约定**，不是平台事实：换一个读法（CLI、导出、别的消费者）就会漏出去。

#### 修法

给消息加一个**定向签名**：带 `direct` 的消息只有发送方与收件方看得到。

- **落在消息的 refs 里**，不新增表、不新增列：`direct` 只是一个签名串（和 `project-goal`、`to-admin` 同一层）；
- **可见性在读路径上判**：服务层的 `list_messages` 按观看人过滤（发送方/收件方可见），
  路由层用令牌的主体作为观看人；没有可识别身份时**看不到**定向消息（失败关闭）；
- **收件人沿用 mention 的投递记录**（`message_deliveries`），不另建一套；
- **不新增事件名、状态、状态迁移边** → `schema_version` 不动（§37.7 只对新增事件提升）；
- CLI 的 `say` 加 `--mention` 与 `--direct`，管理员侧读得到、回得了；
- **自动回**：管理员 worker 的消息循环识别 `direct` 签名，把问题交给管理员自己的模型
  通道，答案仍以定向消息发回；同一问题只答一次（按消息 seq 记账）；模型失败时发一条
  定向消息说明失败原因，不冒充回答，也不把私聊内容写进群回执。

### 38.14 R10-fix-19：人还不能给窗口指定用哪个模型

**来源**：Agent Office 的窗口页 —— 人想给某个窗口定「用自带模型」还是「用额度池里的
哪个模型」，并且要写清楚是哪个池子的什么模型（免费池子标清楚是哪家 harness 内部的
什么模型，付费池子同样）。

#### 缺口

平台没有「给某个窗口指定模型」这件事。

- **模型是 CLI 自己配置里的事实，平台只读**（§7）：`configured_model()` 读的是
  CLI 自己的配置文件，平台从不替它决定用哪个模型；
- **额度池已经在替人挑模型，但那是平台自己挑的**：`plan_attempt()` 只在**上一轮是
  provider 失败**时才从池子里挑一个（免费 → 计量 → 人的 key，且要人点头）。人**没有
  开口子**指定过 —— 池子那条路是「救急路径」，不是「可选清单」；
- **池子里的模型是有主的**：每条都带额度名（`qoder:Qwen3.8-Flash` 这类）与档位
  （free / reserve / metered / user），所以「哪家的什么模型」是平台已有的事实，只是
  从来没摆到人面前。

于是：人能看到池子里有哪些额度，却不能让任何窗口用它们。

#### 修法

给**窗口**（不是任务）加一个「模型来源」的选择：人来定，平台照办。

- **落在 `harnesses` 上**：`model_mode`（`cli` / `pool`）、`model_id`（额度池里的模型
  id）、`model_updated_at`。这是**窗口的登记**，不是任务的状态 —— 任务只管这一轮；
- **迁移**：`017_harness_model_selection.sql`（`ALTER TABLE` 加三列；表的 schema
  版本由迁移编号承载，事件 `schema_version` 不动）；
- **两个取值，不多不少**：`cli`（用这个窗口自己 CLI 配置里的模型，默认）与 `pool`
  （走额度池）。平台不猜，也不替人选；
- **平台照办**：`plan_attempt()` 先看人给这个窗口指定的选择；指定了池子里的某个
  模型，这一轮**直接**走它（不再只在失败之后才换池子）；
- **三条不许**：
  1. **不静默换模型**：指定的模型此刻不在池子里 → 回落到自带，并把原因写进答复；
  2. **不替人花钱**：「你自己的 key」那一档仍然要人点头（§17）；没点头就**问**一次，
     这一轮照旧走自带；
  3. **刚挂掉的模型不用第二次**：指定的模型正是上一轮失败的那个 → 按现状自动挑
     （自动路径本来就会跳过失败的那个）；
- **权限**：复用 `harness:register`（人可用，§17 权限矩阵），**不新增权限键**；
- **不新增事件名、状态、状态迁移边** → 事件 `schema_version` 不动（§37.7 只对新增
  事件提升）。

### 38.15 R10-fix-20：额度池的档位会变，而「免费」不是永久的

**来源**：Agent Office 的窗口页 —— 人给窗口选「用额度池里的哪个模型」之后，主人指出
两件事：**收费额度要能选但要点头**，而且**清单要重探**（「防止之前的免费模型重新收费，
或者加入新的免费模型却不知道」）。

#### 缺口

「免费」只是一个**声明**，而且没人守它。

- **档位是声明出来的**：`app/pool/sources.py` 里每个额度槽自己声明 `tier`
  （`free` / `reserve` / `metered` / `user`）。把某个 `free` 改成 `metered` 只需要改
  一行配置 —— 平台不会发现，人也不会知道。
- **平台的发现结果有缓存，而且没人清它**：发现默认缓存 30 秒
  （`DISCOVERY_TTL_SECONDS`），`invalidate_discovery()` 只在用户增删自己的 key 时被
  调。于是「新的免费额度上线了」与「某个额度改成收费了」这两件事，**都可能一直没人
  知道**。
- **平台照办时不看档位**：`plan_attempt` 只认「人选了哪个模型」，不认「人点头时那一
  档是什么」。所以一个免费额度变成收费额度之后，平台会照旧去花它。
- **只有声明过的那几个模型在池子里**：各家 CLI 自己能用哪些模型（codebuddy 有二十
  几个），平台只提供**声明过**的那几个；多出来的那些既没人看见，也没人定档。

#### 修法

1. **按量计费的额度要人明确点头**：`POST /adapter/model-selection` 收
   `paid_consent`；目标模型是 `metered` 而没点头时**拒**（409
   `model.paid_consent_required`）并说清为什么。这条在**服务端**，界面点不点得到都
   不算数。
2. **记下「点头时那一档」**：`harnesses.model_tier`（迁移
   `018_harness_model_tier.sql`）。照办前核一次：点头时是免费、现在它收费了 →
   **不再花它**，回落到自带并把「要你重新点头」写进答复。
3. **一个探针**：`POST /pool/probe` 清掉发现缓存、重读一遍，并回一份新的清单（含每
   个模型现在的档位）。**只有人点了才探**（探一次要问二十几个上游）。
4. **名册**：`/pool/status` 多给一份 `rosters` —— 各家 CLI 自己说它能跑哪些模型
   （一次列举，不花额度）。名册**不是档位**：CLI 能用 ≠ 免费。办公室拿它跟池子里的
   模型比，把「CLI 还能用、但没人定档」的也报出来。
5. **不新增事件名、状态、状态迁移边** → 事件 `schema_version` 不动（§37.7 只对新增
   事件提升）。

### 38.16 R10-fix-21：额度的声明要能由人当场写下来

**来源**：Agent Office 的窗口页 —— 主人看了 UI-19 的清单后说：「截图里这个也太长了吧，
怎么没有按照对应的harness进行折叠，而且付费额度大把，不只有这点啊」。

#### 缺口

- **清单是按档排的**：二十多个模型摊平成一长串，qoder 的两条被埋在后面看不见（上一轮
  因此被读成「没探全」）。按档排回答的是「哪些免费、哪些收费」，而人问的是「**谁的**
  额度、**谁的**模型」—— 要按额度属主分组。
- **池子只提供声明过的那几个**：codebuddy 的 CLI 自己列得出 20 个模型，opencode 列得出
  44 个；平台上只提供声明过的那几个（codex 8 + claude-provider 1 + opencode 2）。多出来
  那一大批既不能选、也没法定档 —— **免费还是收费是账户里的事实，平台猜不出来**，而人
  一句话就能说清。
- **声明只能手改文件**：`data/pool/config.json` 是人手工维护的，办公室里没有路。

#### 修法

1. **按额度属主分组、每组默认收起**：清单的头写「几家 · 几个可用 · 几个还没定档」，
   每组写「这组几个可用 · 它还能用几个」。
2. **当场定档**：`POST /pool/declaration`（人可用）把「某个名册里的模型是免费还是收费」
   写进 `data/pool/config.json`；写完清发现缓存与名册缓存并重探，那个模型立刻变成一个
   带档位的可选项（标成收费的仍然要点头才能用 —— §38.15 那条闸门不变）。
3. **三条不许**：
   1. **只承认 CLI 自己说能用的模型**：平台不替 CLI 发明模型（定档只对名册里的模型
      开放）；
   2. **沿用同一家的调用约定**：新槽的 argv 契约照抄那家现有的槽（模型不同，程序
      契约不该不同）；
   3. **档位仍是人的决定**：平台不猜；写声明的是人。
4. **不动数据库**：池子的声明是 `data/pool/config.json`，不是表 → **不需要迁移**；
   不新增事件名、状态、状态迁移边 → 事件 `schema_version` 不动（§37.7）。

### 38.16 R10-fix-22：成员说「目标要改」，管理员听不见

**来源**：Agent Office —— 仓库主人：「另外成员harness也可以发信息，不过当成员更改目标时，
管理员要知道」。

#### 缺口

成员窗口**能**发消息（`app.cli say` 就是那个口子，平台也收 `author_kind='harness'`
的消息），但**管理员听不见**：

- **管理员的消息轮询把不是人的消息一律丢掉**：
  `app/admin/worker.py` 里 `if _sender_type(message) != "human": continue` —— 而且
  序号照旧推进，所以那条消息**再也不会被读到**。成员说什么，管理员都不知道。
- **没有办法标出「这条是要改目标」**：CLI 的 `say` 没有 `--ref`，成员即使说了
  「这个目标要改」，管理员也分不出它和别的闲聊。
- **目标本身不该由成员改**（§19：目标是群主的，管理员细化它）—— 所以这条消息
  要做的是**让管理员听见、并把话带给群主**，而不是让成员自己改。

#### 修法

1. **一个消息签名**：`goal-change`（与 `direct` 同住，`app/tasks/service.py`）——
   成员提「目标要改」时带上它；`app.cli say --ref` 让窗口能标出来。
2. **管理员不再把成员的消息一律丢掉**：认出 `goal-change` 的那条 →
   - **知道**（记一次；消息每轮重放，处理过的不再处理）；
   - **把原话带给群主**（在群里发一条，写明是谁说的、要改什么）；
   - **不自己改目标**（目标是群主的）；
   - 群主的回答随后被管理员用来**重新细化**，方案随之修订。
   成员的其他消息只记在运行日志里，不惊动任何人。
3. **不新增事件名、状态、状态迁移边** → 事件 `schema_version` 不动（§37.7 只对新增
   事件提升）；不动数据库 schema（不需要迁移）—— `goal-change` 只是一个消息签名。

  `backend/app/cli/main.py`（`say --ref`）、`backend/app/admin/worker.py`

### 38.17 R10-fix-23：中途来的窗口，管理员不知道；状态栏也没有在线/离线

**来源**：Agent Office —— 仓库主人：「丰富一下状态栏，增加离线，在线状态，增加中途加入
新的harness功能，加入以后通知管理员」。

#### 缺口

- **状态栏只有一个加载时读一次的连接灯**：窗口的在线/离线**根本没有出现在界面上**；
  大厅的窗口名单还把状态**写死**成 `online` —— 不管平台上那个窗口在不在。
- **中途加入没有路**：项目的成员是开工时定下的（`project.members`）。之后新注册的窗口
  会出现在左栏（那里列的是平台上在册的全部窗口），但**不在这个项目里**，也没有办法
  把它加进来。
- **加了人也没人知道**：办公室加人**不通知任何人** —— 管理员既不知道团队多了一个人，
  也不知道有一批活可以交给它。

#### 修法

1. **在线/离线是平台上的事实**：`/adapter/availability` 本来就带每个窗口的 `status`；
   顶栏据此显示「窗口 N 在线 · M 离线」，并**跟着每轮刷新变**；平台读不到时说实话
   （「未连接平台」），不装作一切正常。大厅的窗口名单用同一份事实。
2. **中途加成员**：窗口页给「还没在这个项目里、而且在线」的窗口一个「加入这个项目」；
   加入即写进项目成员。
3. **加入以后通知管理员**：一条带 `add-member` 签名的群消息（含
   `add-member-json:<harness_id>`）。管理员**知道**（在群里说一声）、并把**还在等人
   领的活**改派给它；已经在跑的活不换人。
4. **不新增事件名、状态、状态迁移边** → 事件 `schema_version` 不动（§37.7 只对新增
   事件提升）；不动数据库 schema（不需要迁移）—— `add-member` 只是一个消息签名。
