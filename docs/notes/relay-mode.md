# 转接模式（relay mode）：平台只负责把话送到

状态：M1 已实现（文件信箱 + relay worker）。作者：助理 agent。日期：2026-11-01。

## 0. 传输为什么是**文件**（而不是屏幕、也不是让每个 CLI 调接口）

2026-11-01 做过一组对照：同一个 CLI，同样的问题，两条路各拿到什么。

| | 终端（PTY） | 无头模式 |
|---|---|---|
| 平台拿到的东西 | 120 秒 2911 字节、**173 个控制序列**；用真 VT 模拟器（`@xterm/headless`）重建后**一行可用的都没有** | 结构化输出（JSON 行/字段） |
| 失败时 | 静默：发的人以为送到了，收的人永远没收到 | 有状态码与原因 |

而"写文件"是每个 coding CLI 都会做的一件事，写出来是**干净字节**、写完才被读到（原子），
不需要 VT 重建、不需要网络、不需要令牌 —— 也不需要每个 CLI 都有调平台接口的能力。
所以：**传输用文件，读取用文件，人看的是平台消息**。

## 1. 它是什么

一个**并存的运行模式**：平台不拆任务、不管工作树、不做校验与合并，只把 harness 说的话
按收件人送到该看到的人那里。分工、改哪个分支、谁审谁——是 harness 自己的事。

现有调度链路（方案 → 派单 → 领取 → 校验 → 审批 → 合并闸门）**一条都不改**。模式开关
关闭时，消息完全按今天的样子走。

## 2. 为什么不需要终端

内置终端是**给人用的** PTY：平台在那边只能看到一块屏幕字节流，读不出"这段是给谁的"
（§0 的实测）。所以转接落在**文件**上，终端仍只给人用。

## 3. 信箱目录（全部在 `<仓库>/relay/`，运行时产物，已进 .gitignore）

```
relay/
  outbox/           发送方写这里，一个文件就是一封信
  archive/          投过的信挪到这里（同一封信不会被投第二次）
  returned/         格式不合规/收件人认不出的信挪到这里，旁边附 <名字>.reason.md
  inbox/<窗口id>/   投给这个窗口的信（没有 HTTP 能力的 CLI 直接读这里）
```

## 4. 一封信长什么样

```
来自 codex

给管理员：
这件事要你定方向：口径 A 还是 B。

给 opencode：
我改了 docs/x.md 第 3 段，你接后面那一半。
```

- **第一行必须是 `来自 <窗口 id>`**：文件名不可信（谁都能起名叫 `codex-1.md`），
  而平台**不能**冒充任何人说话；作者由信自己声明，平台验它是已登记的窗口；
- `给<收件人>：` 一行一个块；收件人写**窗口 id**；另有别名 `管理员` / `admin`
  → `AP_ADMIN_SUBJECTS` 里被委托的管理员窗口；
- 块内容是下一个块头之前的全部文字（不做润色，原样转）。

## 5. 投递规则

一个 worker（`python -m app.relay.worker --loop`）扫 `outbox/`，每封信：

1. 收件箱放一份文件：`inbox/<收件人>/<时间>-<原文件名>`，开头一行注明「来自 X（转接于 …）」；
2. 消息面记一条定向消息：**作者是 `relay` 这个已登记的窗口自己**，正文首行写
   「来自 X：」—— 谁说的、谁转的，分得开；界面里因此看得见，`message_deliveries` 照常记录；
3. 信挪进 `archive/`：进程重启也不会重复投。

一份内容两处落地：**人看消息，CLI 读文件**。这是选"文件 + 消息都投"的原因。

## 6. 失败处置（不猜、不兜底）

| 情况 | 处置 |
|---|---|
| 第一行没有 `来自 <窗口 id>` | **整封退回** `returned/`，附原因 |
| 作者不是已登记的窗口 | 整封退回，附原因 |
| 某个块头的收件人不在名册 | 整封退回，原因里列出认不出的名字；**一条都不投** |
| 块内容为空 / 写给发送方自己 | 整封退回（后者防自环） |

退回不是丢掉：信挪进 `returned/`，旁边那份 `.reason.md` 写清为什么没投，改好格式重新
放进 `outbox/` 即可。**不做部分投递**：投了一半，读的人会以为那就是全部。

## 7. 跳数与回路控制（已实现）

转接是双向的：A 写给 B、B 回给 A，平台会一直投下去 —— 没人做错事，但对话永不结束。
两道刹车，缺一不可：

1. **显式线程**（精确）：投递时平台分配 `thr-xxxxxxxx`，并写进收件箱那份文件的最上面
   （`线程 thr-… · 第 N 跳（回信请写：回复 thr-…）`）与消息 refs（`thread:` / `hop:`）。
   回信写 `回复 thr-…` 就接上同一条线程，跳数 +1；**到了 `MAX_HOPS`（6）整封退回**，
   理由写明"先停下让人看一眼；要接着谈请当成新的事重新起一封"。
2. **回路闸门**（不依赖协议）：模型会忘记写线程，所以另有一道与协议无关的限制 ——
   同一对窗口在 10 分钟内来回超过 `MAX_EXCHANGES`（6）次就停，同样整封退回。

两条都**整封退回 + 说清原因**（写进 `returned/<名字>.reason.md`），不静默丢弃、也不
继续投。账本落在 `relay/threads/<thread>.json`，worker 重启后跳数仍然准确。

**退回不占用额度**：闸门先"预看"再记账，整封被退回时，那些还没收到信的窗口一次都不记。
否则反复改格式重发会把额度耗光 —— 改对了也进不来，那就把刹车变成了锁死。

一个实测出来的区分：**账本坏了 ≠ 线程不存在**。前者是平台侧的问题（比如账本被手改坏），
后者是写信人抄错了 id；合并成一句"线程不存在"会让人反复改 id 也改不对。所以现在分开
报，账本读不出来时明说"请平台方看一眼"。

## 8. 开关与验收

- `AP_RELAY_MODE=1` 表示"这台机器上跑转接"，默认关闭；关着时平台行为与今天一致
  （worker 不启动，消息面不解析任何格式）；
- 验收 `tests/test_relay_mode.py`（16 条）：块拆分与 `管理员` 别名、非信封不误判、
  未知收件人/空块/自环整封退回、作者行与 BOM、投递后收件箱与消息各一份且作者是 relay、
  抄送群主、未登记作者退回、投过的信不重复投、**同线程回信跳数 +1、到 `MAX_HOPS` 停下、
  抄错的线程 id 退回、账本坏了按平台侧问题报、同一对窗口来回超限被回路闸门停下、
  退回的信不占用没收到的窗口的额度**。

真平台实测（8848 + flow-1101-g1，2026-11-01）：

- 第一封 → `thr-4dc2fb1f` / 第 1 跳，收件箱那份文件最上面带「回信请写：回复 thr-…」；
- 按提示回信 → 同一线程第 2 跳，账本 `hops: 2`、参与者 `codex`/`opencode`；
- 把账本推到 6 跳后回信 → 退回：「已经转了 6 跳（上限 6），先停下让人看一眼再继续」；
- 连发 7 封新信给同一窗口 → 前 6 封投出，第 7 封退回：「10 分钟内已经来回 7 次（上限 6）」。

## 9. 每项目一条路：新建项目时的「协作方式」（已实现）

转接原来只是**这台机器**上的一个开关（`AP_RELAY_MODE`），人看不出某个项目到底走哪条路。
现在路径在**建项目时选**，写在项目上：

- 「项目配置」里，运行数据源后面多了「协作方式」，两个选项：
  **派单协作**（默认，平台拆解任务、分派、校验、合入）与
  **转接**（平台只当邮局，成员之间写信转达，不建任务、不开工作树、不判内容）；
- 选转接之后：执行成员那一栏与「项目范围」提示收起（转接没有任务、没有成员范围可言），
  底部按钮变成「创建并进入转接视图」，创建完**不进开工向导**、顶栏也不放「开工配置」
  —— 转接没有任务目标可写，留一个点了没事干的按钮比没有按钮更糟；
- 转接项目进入的是**转接视图**（`office/src/relay-workspace.js`），只有四块：
  在不在跑 / 写信的格式 / 线程 / 退回。长清单默认收起、标题写明几条。

为什么转接要单独一页：转接投出来的消息带 `direct` 签名，而项目群聊面板按 §19 会把它
过滤掉（`flat-office.js:5617`），管理员对话与助手线程也只认各自的收件人 —— 所以转接
其实**在派单那套界面里一条都看不到**。抄送群主救不回来，必须另给一处只读的地方。

「在不在跑」是事实不是猜：relay worker 每轮轮询都会碰一下 `relay/.worker-heartbeat`，
超过 5 分钟没动就按「已经停了」显示，并写明「这段时间放进去的信不会被投递」。

数据只走一条只读接口 `GET /api/formal/relay/overview`（`office/server/relay-overview.mjs`）：
读 `threads/*.json`、`returned/*.reason.md`、`outbox/` 数量与心跳。三条口径：
坏账本照样列出来并标「读不出来」（不是悄悄少一条）、原因读不到就照实说没写清楚、
一个字节都不写。

信箱位置默认 `<仓库>/relay`；换地方用 `OFFICE_RELAY_ROOT` 指过去，必须与 relay worker
的 `--root` 是同一个目录，否则界面读的是另一份信箱，会显示"没有线程"而信其实在别处。

验收：`office/scripts/verify-relay-overview.mjs`（8 条：缺信箱、无心跳/心跳过期/心跳新鲜、
坏账本露出、线程按新的在前、退回原因与所属信件、原因文件读不出时不编、只有 .md 才算待投）。

## 10. 本版仍不做

- 不做重放/补投（归档里有原件，但没有重发机制）；
- 不改 §19 的读权限：定向消息仍然只有两端（+ 抄送的群主）看得到；
- 转接视图**不发信**：写信仍是成员自己的动作（或人自己在终端里写）。界面只读，
  不提供"替某个人发一封"的按钮 —— 那会让平台变成代笔的。
- 转接与派单**互斥在项目层面**，不是同一项目里混着跑：选了转接的项目不建任务，
  选了派单的项目不转接。要混着用是另一件事，先别做。

## 11. 谁把转接跑起来：管理员（已定，已实现）

**答案：管理员窗口。** 具体是管理员自己的 worker（`app.admin.worker`）每轮开头
（60 秒最多一次）确认转接在不在跑，没在跑就把它拉起来（`app/relay/supervisor.py`）。
办公室界面**没有**"把转接跑起来"的按钮，也不该有：那是运维动作，界面是人看的地方，
不是人值守的地方 —— 人点一次能拉起一个，机器重启之后照样没人管。

三条口径写在代码里：

1. **管理员只开关，不代笔**：投递仍是 `relay` 窗口自己的身份（作者=令牌主体），
   管理员从不替谁说话，也不改信一个字。所以拉起前必须先有 `data/relay.key`；
   没有就**不动手**并说明原因，绝不拿管理员的令牌顶上去。
2. **幂等，群级单例**：两个 worker 读同一个 `outbox/` 会把同一封信投两遍。判定分两档 ——
   心跳新鲜 = 正在投递；进程还活着但没打心跳 = 正在启动（第一次启动要几秒），
   这一档也**不再起第二个**。Windows 上不能用 `os.kill(pid, 0)` 探活（那是 TerminateProcess），
   走 `OpenProcess + WaitForSingleObject`。
3. **开关仍是 `AP_RELAY_MODE`**：没开就不动手。

信箱与凭据的位置：`AP_RELAY_ROOT` / `AP_RELAY_TOKEN_FILE`，默认 `<仓库>/relay` 与
`data/relay.key`；`OFFICE_RELAY_ROOT` 是界面那一侧的同一个开关，两边必须指同一个目录。

验收：`tests/test_relay_supervisor.py`（已在跑不重复起、心跳过期才起、没有 relay 凭据不动手、
起了但心跳没来要如实说、进程活着没心跳不重复起、spawn 失败说原因、开关解析、目录与凭据的
环境变量）。真跑过两次：删掉心跳后 ensure → 起得来、有心跳、pid 落盘；紧接着再 ensure →
「已经在跑，不重复启动」；管理员 worker 本身跑一轮也打印了同一句（在 scratch 信箱上验的）。

## 12. 转接项目跟着仓库走（已定，已实现）

定的口径：**以仓库为准**。转接的信在仓库里，项目也不该只活在浏览器记忆里。

- 新建转接项目时，办公室把项目名写进 `<relay>/project.json`（`{name, created_at,
  updated_at}`，**不记成员、不记凭据**）。写不进去就当场说、并且**不建项目** ——
  别让"项目在仓库里"只是嘴上说说；
- 大厅读 `GET /api/formal/relay/overview` 里的 `project`，凡是"仓库里有、这台浏览器
  没记录"的转接项目，照常列一条，标「来自仓库」并写明「本机没有这个项目的记录，
  按信箱打开」；点开就在本地建一条入口，走同一个转接视图。这样换一台机器 clone 下来，
  历史里没人记也不影响看得见信箱。
- 改名保留 `created_at`：那是这个项目在仓库里的出生时间，不该被改名改掉。
- 只认 `project.json` 这一份文件，**不扫全仓库**；读不出来就说读不出来（写进
  `project_note`），不静默当成"没有项目"。

一个仓库 = 一个信箱 = 一个转接项目。多个项目共用一个 `relay/` 是另一件事，先不做。

验收：`office/scripts/verify-relay-overview.mjs` 12 条（新增：写入并读回、改名保留
created_at、项目文件坏了要说、空名字拒绝）；真平台也走过一遍 —— POST 写进
`relay/project.json`（中文正确、created_at 稳定），大厅里出现「来自仓库」那张卡，
点开直接进转接视图。

## 13. 待确认（需要人拍板，不替他假设）

1. **一封信写给多个窗口**时，现在抄送群主只抄一份；若以后要"每个收件人各看各的"，
   得先改 §19 的读权限口径。
2. **大厅没有"删除项目"**：项目只增不减（本地记录与 `project.json` 都没有删除入口）。
   验证时留下的本地记录只能靠清站点数据去掉 —— 要不要给一条明确的删除路径，尚未定。
