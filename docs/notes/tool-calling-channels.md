# 工具调用：三条路，以及我们站在哪一条上

这份文档回答一个真实发生过的问题：**某个窗口的模型给不出 `tool_calls`，怎么办？** 以及顺着它来的第二问：**平台该不该替模型执行工具？**

写它的原因是我们在没查之前先做了一个实现（`backend/app/agenttools/`，基座 `platform`），后来才发现业界有三种做法、我们只走了其中一种的一半。先把对照摆清楚，再决定接下来改什么，比直接往下加代码省事。

---

## 一、三条路

### 路 1：解析器放在推理服务端

模型输出它自己在训练里见过的**文本**格式，由**推理服务器**把这段文本解析成结构化的 `tool_calls`，应用层看到的仍是 OpenAI 那套结构。

- **vLLM**：`--tool-call-parser hermes|mistral|llama3_json|pythonic|glm45|glm47|qwen3_xml|functiongemma|mimo|step3p5|olmo3|…`，配 `--enable-auto-tool-choice`；还提供 `--tool-parser-plugin` 让使用者**自己写解析器**。参数 `strict` / `--tool-strict-level` 用来把参数约束到 schema。
- **llama.cpp**：JSON-Schema → GBNF 语法约束输出（采样阶段就拒绝不合法的 token），再用 PEG 解析器把文本还原成 `tool_calls`；"这个模板该用哪种工具格式"由 autoparser 分析 Jinja 模板自动判断。
- **Ollama**：走 OpenAI 的工具格式，但它不做语法约束，全靠模型训练过——所以"原生支持"和"稳定可用"是两件事。

**这一条最值得记住的事实**：所谓"原生 function calling"，模型产出的仍然是文本，只是换了一种约定格式；把它变成结构体的那一步，永远有一方在做。有篇讲本地函数调用的文章把这点说得很直白：**"函数调用不是模型伸手去碰你的文件系统，是你的编排层在调。"**

### 路 2：解析器放在客户端 / 网关

模型或上游确实给不了工具调用，就在调用方把工具定义**塞进提示词**，再把回复里的文本解析回工具调用。

- **LiteLLM** 有 `litellm.add_function_to_prompt = True`，文档的说法是"对任何不支持函数调用的模型/提供商"都可用。
- ⚠️ 但社区有 issue 指出：在 v1.103.2 里这个开关只在 ollama 分支被读到，文档与实现不一致。**要用先自己验**，别照文档信。

### 路 3：根本不当模型用

CLI 本来就是一个 agent（它有自己的工具、自己的循环、自己的沙箱）。协议层早有标准：

| 协议 | 连的两端 | 形态 |
|---|---|---|
| **ACP**（Agent Client Protocol） | 编辑器 ↔ agent | JSON-RPC over stdio，agent 是被管理的子进程 |
| **MCP**（Model Context Protocol） | agent ↔ 工具/数据 | 服务端可以本地 stdio，也可以远程 HTTP |
| **A2A**（Agent2Agent） | agent ↔ agent | 任务委派 |

这三层是**互补**的，不是三选一。把一个 agent 伪装成 chat completion endpoint（也就是"CLI 顶替模型"），是这三条里最别扭的一条。

## 二、我们现在站在哪

### `platform` 基座（`backend/app/agenttools/`）

属于**路 1 的一半 + 路 3 的退化版**：

- 工具由平台执行、模型只输出一个 JSON 对象——这相当于把"解析器"放在平台（路 1 的做法，只是服务端换成了我们）；
- 但为了做到这点，平台还得**补上一个 agent 的循环**，因为被路由过来的通道连"调用工具"这一步都产不出来。

它的合法性与局限：

- 合法：和 vLLM/llama.cpp 那一层同构，不是野路子；真跑过四条路径（交付、驳回返工、合入、当审阅者），有凭证。
- 局限：它解决的是**通道残缺**，不是**工具不够**。一旦需要它，说明平台已经越过了"只调度"这条线。

### 额度池里的 `cli` 协议

属于**路 3 的错误用法**：把另一个 CLI 当成模型来问。

代价是实打实发生过的：那条通道给不出 `tool_calls`，于是池子曾给它灌 "Do not use tools, do not read or write files"，结果窗口"零交付"——一个 agent 被当成哑巴模型用，两头都亏。

## 三、接下来该做什么（建议，未决）

1. **MCP 作为主路**：把平台的能力（文件/搜索/命令/git 只读/交活/查任务上下文/读评审意见）做成 MCP 服务，让 `claude` / `opencode` / `pi` / `codebuddy` 用**自己原来的循环**去调。平台的定位回到"提供工具 + 判范围"，循环留在 harness 里。
2. **`platform` 兜底保留但降级**：只在"这条通道确实产不出 `tool_calls`"时启用，并且**在界面上写明**「这个窗口的工具由平台代执行」——让人一眼知道发生了降级，而不是以为自己在用某个 CLI。
3. **`cli` 协议要么标注、要么删掉**：它制造的问题比解决的多。若保留，界面上必须写成"降级通道（借某个 CLI 的额度当模型）"，不能叫"免费模型"。
4. **不做**：不把解析器塞进模型服务那一层（我们不是推理服务），也不假装自己能替模型训练格式偏好。

## 五、没定的事

- MCP 的形态选哪个：远程 streamable HTTP（多窗口共用、便于审计）还是每窗口一个 stdio 子进程（隔离强、不用鉴权）。这决定平台要新增一个路由还是一套进程管理。
- 平台工具要不要在 MCP 里额外暴露"平台才知道的东西"（任务书、验收条款、评审意见、额度用量）——那才是 CLI 自己给不出的能力。
- `cli` 协议删不删。删掉意味着某些"免费额度"用不了；不删意味着永远有一条会把 agent 当模型的通道。
