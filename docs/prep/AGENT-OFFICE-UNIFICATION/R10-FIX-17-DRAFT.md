# R10-fix-17 草案：任务接替关系进平台字段

状态：**已落 R10 正文**（§9「任务接替关系（`supersedes`）」、§38.12「R10-fix-17」）。
本文原是"登记输入"（**不代表规范已批准**）；2026-10-22 由**仓库主人**拍板，第五节的
五条待裁问题按下面的落定结论写进 R10 正文，本文因此转为该次裁定的记录。
本文**不新增事件名、不新增状态、不新增状态迁移边**；它给既有的任务**快照**加一个
可选字段（`supersedes`），并给派单请求加一个可选字段。

---

## 0. 一句话

改派（管理员取消旧任务、按同样的规格派一条新的）目前只在**群里的一句话**里留下
接替关系，平台自己不知道谁接替了谁。改为：新任务在**派单时**声明 `supersedes`，
该字段写进它的**计划快照**（任务的不可变契约），任务列表与任务详情都投影它。

## 1. 缺口

- 现状：改派 = `cancel` + `dispatch` 两步既有动作 + 群里一条说明。
  **"谁接替了谁"没有平台字段**：
  - 旧任务的 `cancel` 事件带的是**理由**，没有"接替者"——派单发生在取消**之后**，
    那一刻新任务还不存在；
  - 新任务的事件里也没有"接替了谁"；
  - 于是任何消费方（办公室、以后的调度器）要还原接替链，只能去**读消息文本**
    （"管理员 Harness 改派：FD-x → FD-y"）——那不是平台事实，是一句话。
- 结果：一条活被换来换去以后，"它从哪来"要一条条读事件流；机器答不出
  "FD-x 被谁接替了"。

## 2. 规范变更

| 位置 | 现在 | 改后 |
|---|---|---|
| 派单请求体（`FormalDispatchRequest`） | 无 | `supersedes: str \| None = None`（可选） |
| 任务快照的 task spec | 无 | `supersedes: "<task_id>"`（可选，仅改派时写） |
| 任务列表投影 | 标题 | 标题 + `supersedes`（可选） |
| 任务详情投影 | `spec` | `spec` + 顶层 `supersedes`（可选） |

- **不新增事件名、状态、状态迁移边**；不新增 canonical 表；不新增列。
- 数据落在**计划快照**里：快照是任务的**不可变契约**，而"这条任务接替那一条"
  本来就是契约的一部分——新的执行者要在工单里读到它，接着上一个 attempt 的
  断点报告继续干（`_goal_with_handoff` 已经在把断点报告写进 goal）。
- **方向**：链接只挂在**新**任务上，旧任务不动。终态任务（`cancelled` /
  `abandoned` / `stale`）的行不被改写——改它就是改历史。
- **校验**（`backend/app/adapter/dispatch.py`）：
  - 旧任务必须**存在**；
  - 必须在**同一个群**（不跨群泄露）；
  - 必须处于"工作没有交付"的状态（`cancelled` / `abandoned` / `stale` /
    `changes_requested`）——**还在跑的活不能被接替**，那会变成两个主人。
- **幂等**：`supersedes` 进请求摘要，但**只在有值时**进。没有链接的请求必须与
  字段存在之前哈希完全一致，否则旧 `request_id` 的幂等重放会变成"同 id 不同
  内容"的冲突。

## 3. 实现与测试

- `backend/app/adapter/dispatch.py`：请求加 `supersedes`；三条校验；写进 spec。
- `backend/app/api/schemas.py`：`FormalDispatchRequest.supersedes`（可选，≤64 字）。
- `backend/app/tasks/service.py`：`_titles_for` 在**同一次快照查询**里多投影
  `supersedes`；`get_task` 顶层也投影一次。
- `backend/app/admin/worker.py`：改派时传 `supersedes=旧任务 id`。
- 前端网关：`safeTask` 加 `supersedes`；办公室的「这条活的来路」**优先用平台
  字段**，改派之前的老数据回落到群消息（并标明那是管理员的说法，不是平台字段）。
- 测试（`backend/tests/test_formal_dispatch.py`，4 条）：
  接替关系被列表与详情投影 / 活着的任务不能被接替 / 不存在或跨群的旧任务被拒 /
  无链接的请求哈希与从前一致。

## 4. 真实平台验证

待补：实机跑一次管理员改派，确认新任务的列表项与详情都带
`supersedes=FD-<旧任务>`，且旧任务那一行**没有**被改写。

## 5. 待复审（请复审者裁这五条）

**已裁（2026-10-22，仓库主人）**，落定结论与理由：

1. `supersedes` 该落在**快照**（任务的契约），还是新建一张 `task_reassignments`
   表（一张表记多条接替、连理由一起记）？前者不动 canonical schema，后者要加表
   （R10 §8 表清单 41 → 42）。**落定：快照**（改动面最小，且链接随任务不可变）。
2. 链接只挂**新任务**是否可以？旧任务要不要也能直接回答"我被谁接替了"？那需要
   反向列或第二列。**落定：只挂新任务 + 消费方在列表里反查**（终态任务的行不被
   改写——改它就是改历史）。
3. "工作没有交付"的四个状态（`cancelled` / `abandoned` / `stale` /
   `changes_requested`）够不够？**落定：就这四个**（`escalated` / `awaiting_human`
   仍可能有在跑的 attempt，接替它们会变成两个主人）。
4. 快照里的这个可选字段要不要进 R10 §9 的方案契约？**落定：要**（已写进 §9）。
5. 事件 payload 要不要也带 `supersedes`（那会让 `plan.approve` 的
   `schema_version` 升到 2，并要动 R10 §37.7 附近的正文）？**落定：不带**——
   快照已经够用，`plan_version` 仍是 v1，**不提升 `schema_version`**。
