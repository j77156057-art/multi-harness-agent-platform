01 / 问题

协作失控，往往发生在边界不清的地方

多个编程窗口同时工作时，失败模式高度相似：没人说得清谁拥有写入权、旧结果会不会复活、测试通过是否等于可以合并。

ISSUE 01

两个窗口同时领取同一任务，最后谁的结果有效说不清。

ISSUE 02

窗口崩溃或网络中断后，任务卡在“有人负责”的状态，其他人无法接手。

ISSUE 03

旧窗口恢复后继续写入，覆盖已经接管任务的新窗口结果。

ISSUE 04

测试通过与允许合并之间，缺少一条可核对的证据链。

ISSUE 05

不同 Harness 的 CLI、输出格式和工作区各不相同，接入一个就要写一套特殊逻辑。

ISSUE 06

只看最终状态无法解释“谁在什么时候做了什么”，排障只能靠猜。

04 / 核心机制

每条机制都有对应的测试证据

机制不是文档里的承诺，而是可以被机械核对的约束。下方每张卡片都附上验证它的测试文件与用例名。

并发领取去重

一次领取请求带唯一请求标识，重复或竞态的领取被收敛到同一个结果上：同一份工作只允许一个赢家。

backend/tests/test_claim_concurrency.py
test_only_one_of_two_racing_claims_wins

租约与接管

持有权变成带有效期的租约。租约过期后原持有者状态失效并释放全部资源，其他成员可安全接管，避免单点失联造成死锁。

backend/tests/test_lease.py
test_expiry_moves_an_owner_state_to_stale_and_frees_everything

fencing 防旧写入

每次写入携带 fencing 世代。旧持有者的迟到写入——无论续租还是绕过租约路径的受保护写入——都会被直接拒绝。

backend/tests/test_lease.py
test_renew_with_a_stale_fencing_epoch_is_refused

验证与人工审核分离

验证只产出“能否进入审核”的结论，审核只由人在验证通过之后进行。两者职责互不替代，谁也不能越过谁。

backend/tests/test_verify.py
test_failing_head_cannot_reach_review

事件流可重放

事件序号单调递增、只追加写入，任何投影都可由事件重新推导。投影损坏时，一条命令即可从事件日志重建。

backend/tests/test_database_events.py
test_event_store_is_append_only_and_replayable

分配治理与合并互斥

领取必须建立在已接受的分配之上；并发争抢合并权时恰好只有一个赢家，绝不允许两份互不兼容的状态被揉在一起。

05 / 架构与数据流

差异止步于适配器，约束集中在平台

每个 Harness 只需说同一种协议；领取、租约、校验、审核、合并与事件写入都在平台侧完成，工作区与主分支物理隔离。

领取与写入资格 验证与审核门禁 合入与产出 事件与回溯
物理隔离每个 attempt 在独立 worktree 中实现，主分支只接受通过验证与审核的 commit。
状态在服务端窗口失联不影响任务归属；租约由平台时钟判定，过期即可接管。
证据可复现合并边界、review lease 与被审 commit 一一对应，事后可完整复核。
06 / 事件流

不只回答“现在是什么状态”，还回答“为什么”

下面这条事件流取自真实任务：同一件事从方案批准到合入主分支，八个动作、四个执行者，序号单调递增。

#6285plan.approve 方案被批准，任务快照冻结codebuddy · 20:12:05
#6286claim 领取成功，创建 attempt / lease / epochclaude-code · 20:12:07
#6287start 在隔离 worktree 中开始执行claude-code · 20:12:09
#6288submit_result 提交结果与 commit，生成回执claude-code · 20:19:01
#6289verify_passed 按 profile 校验通过，允许进入审核verify-worker-1 · 20:19:17
#6290approve 人工审核通过，review lease 与被审 commit 一致codebuddy · 20:20:13
#6291merge_start merge worker 取得合并权merge-worker-1 · 20:20:14
#6292merge_success 已合入主分支，任务完成merge-worker-1 · 20:20:22

只追加，可重放

事件表只写不改，序号全局单调。任何投影都能由事件重新推导出来。

投影可重建

用最新 checkpoint 加上后续事件重放，写出一个完整新库，并对 15 张聚合表逐列 diff：

python -m app.tools.rebuild --snapshot --verify

失败也留痕

退回、拒收、接管、续租失败都写进同一条流，排障不用靠猜。

07 / 工程能力

把“谁能写入”变成可检查的状态，而不是约定

每一项能力都对应项目中的具体实现与明确的设计关注点。

并发领取

SQLite 事务、条件更新与请求幂等记录，两个真实连接抢同一任务时只创建一个 attempt。

租约与接管

lease token、平台时钟、过期扫描与 epoch 递增，租约过期后旧窗口不再拥有写入权。

防止旧写入

guarded write + fencing epoch + attempt 校验，接管发生在请求途中也不会丢失隔离。

结果验证

verify profile、命令白名单与 verification receipt，未验证的提交不能直接进入 review 或 merge。

人工审核

review lease、commit 一致性与权限矩阵，审核身份和被审核 commit 都必须可确认。

受控合并

canonical repo、隔离 worktree 与 merge worker，合并边界和证据都可以复现。

事件追踪

append-only event store、全局 seq、checkpoint + reducer，15 张任务聚合表可重建并逐列 diff。

多 Harness 适配

注册表、统一 adapter protocol 与 CLI 输出解析，把不同 CLI 的差异限制在适配器边界内。

运行期巡检

runtime driver、sweeper 与 liveness / budget 检查，持续推进状态并发现卡住的执行。

可观察界面

Agent Office + 本地预览网关，查看任务、成员、事件、输出与额度，不暴露内部凭据。

自建产品

目标 → 细化 → 传阅 → 派单 → 评审 → 合入，把一句话目标变成可运行、可验证的产品。

幂等重试

请求级与任务项级两层记录，同一请求重放返回原结果，内容不一致则拒绝。
